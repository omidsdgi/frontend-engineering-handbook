Core Question

چگونه Dependencyهای یک JavaScript Project را مدیریت کنیم؟

مقدمه

تا اینجا JavaScript را عمدتاً از دید زبان بررسی کردیم.

یعنی با مفاهیمی مانند:

Values
Variables
Functions
Arrays
Objects
Classes
Modules

آشنا شدیم.

اما یک پروژهٔ واقعی معمولاً فقط از کدی که خودمان نوشته‌ایم تشکیل نمی‌شود.

فرض کنید در یک پروژه به قابلیت خاصی برای کار با تاریخ، ارسال درخواست HTTP یا پردازش داده‌ها نیاز داریم.

از نظر فنی می‌توانیم همهٔ این قابلیت‌ها را خودمان پیاده‌سازی کنیم.

اما در یک پروژهٔ واقعی معمولاً این کار منطقی نیست.

اگر یک قابلیت عمومی قبلاً توسط دیگران پیاده‌سازی و منتشر شده باشد، بهتر است بتوانیم آن را دریافت و در پروژهٔ خود استفاده کنیم.

اینجا یک سؤال جدید شکل می‌گیرد:

چگونه کدی را که توسط دیگران نوشته شده است به پروژهٔ خود اضافه کنیم؟

برای پاسخ به این سؤال ابتدا باید بدانیم چنین کدهایی در JavaScript چگونه بسته‌بندی و منتشر می‌شوند.

این ما را به مفهوم Package می‌رساند.

Package

یک پروژهٔ JavaScript می‌تواند شامل کدی باشد که برای استفاده در پروژه‌های دیگر نیز مناسب است.

برای مثال، ممکن است یک توسعه‌دهنده مجموعه‌ای از Functionها را برای کار با تاریخ ایجاد کند و بخواهد آن را در اختیار دیگران قرار دهد.

برای این کار، کد باید به شکلی قابل توزیع و قابل استفادهٔ مجدد ارائه شود.

به چنین واحد قابل توزیعی در اکوسیستم JavaScript، Package می‌گوییم.

Package فقط چند خط کد نیست.

یک Package معمولاً شامل کد، اطلاعات مربوط به آن و فایل‌هایی است که مشخص می‌کنند چگونه باید در یک پروژه استفاده شود.

بنابراین:

Package یک واحد قابل توزیع از کد و اطلاعات مرتبط با آن است که می‌تواند در پروژه‌های دیگر مورد استفاده قرار گیرد.

اکنون مسئلهٔ اول حل شده است.

می‌دانیم کدی که دیگران می‌توانند در پروژهٔ خود استفاده کنند، می‌تواند به شکل یک Package منتشر شود.

اما هنوز یک سؤال مهم باقی می‌ماند:

اگر هزاران Package وجود داشته باشد، این Packageها کجا قرار می‌گیرند؟

Registry

اگر هر توسعه‌دهنده Package خود را در یک مکان متفاوت منتشر کند، پیدا کردن و دریافت آن بسیار دشوار خواهد بود.

ما به یک مکان مرکزی نیاز داریم که Packageها در آن منتشر، نگهداری و قابل جست‌وجو باشند.

این نقش را Registry بر عهده دارد.

Registry سرویسی است که Packageها در آن منتشر و از آن دریافت می‌شوند.

در اکوسیستم JavaScript، npm Registry یکی از مهم‌ترین Registryها است.

به این ترتیب، مسئلهٔ قبلی به شکل زیر حل می‌شود:

Package
↓
Publish
↓
Registry
↓
Find / Download

اکنون می‌توانیم Package را در Registry پیدا کنیم.

اما هنوز یک مشکل عملی وجود دارد.

فرض کنید بخواهیم یک Package را دریافت کنیم.

آیا باید خودمان به Registry متصل شویم، فایل‌های Package را پیدا کنیم، آن‌ها را دریافت کنیم و در پروژه قرار دهیم؟

واضح است که انجام دستی این فرآیند مناسب نیست.

پس به ابزاری نیاز داریم که این ارتباط را برای ما مدیریت کند.

npm

برای مدیریت Packageها در اکوسیستم JavaScript، ابزار npm در اختیار ما قرار دارد.

npm مخفف Node Package Manager است و یکی از ابزارهای اصلی مدیریت Packageها در اکوسیستم JavaScript و Node.js محسوب می‌شود.

npm می‌تواند با Registry ارتباط برقرار کند و عملیات مربوط به Packageها را برای پروژه انجام دهد.

برای مثال، اگر پروژه به یک Package نیاز داشته باشد، می‌توانیم از npm برای نصب آن استفاده کنیم.

به‌صورت مفهومی:

Project
↓
npm
↓
Registry
↓
Package
↓
Project

بنابراین npm خودش Package نیست.

npm ابزاری است که فرآیند مدیریت Packageها را برای پروژه انجام می‌دهد.

اما حالا یک مشکل جدید ایجاد می‌شود.

فرض کنید یک پروژه پنج Package مختلف دارد.

بعد از مدتی، فرد دیگری پروژه را دریافت می‌کند.

او از کجا باید بداند این پروژه به چه Packageهایی نیاز دارد؟

نمی‌توانیم انتظار داشته باشیم توسعه‌دهندهٔ جدید از روی کدها تک‌تک Dependencyها را پیدا کند.

پروژه باید جایی داشته باشد که نیازمندی‌های آن را به‌صورت مشخص اعلام کند.

اینجا به یکی از مهم‌ترین فایل‌های یک JavaScript Project می‌رسیم:

package.json

package.json

package.json فایلی است که اطلاعات و نیازمندی‌های اصلی یک JavaScript Project را توصیف می‌کند.

برای مثال، پروژه می‌تواند در این فایل مشخص کند:

نام پروژه چیست.
نسخهٔ پروژه چیست.
به چه Packageهایی وابسته است.
نسخهٔ مورد انتظار Packageها چیست.
چه Scriptهایی برای اجرای عملیات پروژه وجود دارد.

بنابراین package.json فقط یک فایل تنظیمات ساده نیست.

این فایل بخشی از قرارداد پروژه با اکوسیستم Packageها است.

وقتی پروژه‌ای را دریافت می‌کنیم، یکی از اولین چیزهایی که باید بدانیم این است:

این پروژه به چه Packageهایی نیاز دارد؟

package.json پاسخ این سؤال را در اختیار ما قرار می‌دهد.

Dependency

اکنون می‌توانیم رابطهٔ بین Package و Project را دقیق‌تر کنیم.

فرض کنید پروژهٔ ما برای انجام یک کار مشخص به Package خاصی نیاز دارد.

این Package بخشی از کد خود پروژه نیست، اما پروژه برای انجام وظیفهٔ خود به آن وابسته است.

به این رابطه Dependency می‌گوییم.

Dependency یک Package یا وابستگی خارجی است که پروژه برای اجرای قابلیت‌های خود به آن نیاز دارد.

برای مثال، اگر پروژهٔ ما برای انجام یک وظیفه از Package خاصی استفاده کند، آن Package یکی از Dependencyهای پروژه محسوب می‌شود.

در package.json این Dependencyها ثبت می‌شوند.

به‌صورت مفهومی:

Project
↓
needs
↓
Dependency
↓
Package

اکنون اگر پروژه در اختیار توسعه‌دهندهٔ دیگری قرار بگیرد، او لازم نیست حدس بزند چه Packageهایی مورد نیاز هستند.

اطلاعات مورد نیاز در package.json ثبت شده است.

اما هنوز یک مشکل مهم وجود دارد.

فرض کنید پروژه امروز از یک Package استفاده می‌کند و نسخهٔ فعلی آن 4.17.21 است.

اگر شش ماه بعد نسخهٔ جدیدی از همان Package منتشر شود، آیا پروژه باید همیشه آخرین نسخه را دریافت کند؟

پاسخ لزوماً مثبت نیست.

ممکن است نسخهٔ جدید تغییراتی داشته باشد که رفتار پروژه را تحت تأثیر قرار دهد.

بنابراین فقط دانستن نام Dependency کافی نیست.

پروژه باید بداند کدام Version از آن Dependency را می‌خواهد.

اینجاست که Versioning اهمیت پیدا می‌کند.

Versioning

Packageها در طول زمان تغییر می‌کنند.

ممکن است Bug آن‌ها اصلاح شود، قابلیت جدیدی اضافه شود یا حتی رفتارهای قبلی تغییر کنند.

بنابراین Package فقط یک نام ندارد.

هر نسخهٔ منتشرشده از Package باید قابل تشخیص باشد.

برای این کار از Version استفاده می‌شود.

یکی از رایج‌ترین الگوهای Versioning در اکوسیستم JavaScript، Semantic Versioning یا SemVer است.

ساختار کلی آن:

MAJOR.MINOR.PATCH

برای مثال:

4.17.21

سه بخش دارد:

MAJOR
MINOR
PATCH

هر بخش بیانگر نوعی از تغییر است.

به‌صورت کلی:

MAJOR
→ تغییرات ناسازگار

MINOR
→ قابلیت جدید با حفظ سازگاری

PATCH
→ اصلاح Bug و تغییرات سازگار

هدف Versioning این است که پروژه بتواند دربارهٔ Dependencyهای خود کنترل بیشتری داشته باشد.

اما اگر پروژه مجبور باشد دقیقاً یک Version مشخص را نگه دارد، مدیریت Dependencyها می‌تواند بیش از حد محدود شود.

برای همین npm امکان تعریف Version Range را نیز فراهم می‌کند.

برای مثال ممکن است در package.json با چیزی مانند این مواجه شویم:

"lodash": "^4.17.21"

علامت ^ نشان می‌دهد که پروژه یک Range از Versionهای سازگار را می‌پذیرد، نه اینکه الزاماً فقط همان Version دقیق را بخواهد.

بنابراین package.json فقط نمی‌گوید:

این Package را لازم دارم.

بلکه می‌تواند بگوید:

این Package را با این محدودهٔ Version می‌خواهم.

این موضوع برای مدیریت Dependencyهای پروژه بسیار مهم است.

اما حالا یک مسئلهٔ دیگر باقی می‌ماند.

تا اینجا دربارهٔ نصب و مدیریت Packageها صحبت کردیم.

ولی پروژه فقط Package نصب نمی‌کند.

ما دائماً عملیاتی مانند اجرای Development Server، اجرای Test یا ساخت Production Build را انجام می‌دهیم.

اگر برای هرکدام مجبور باشیم Commandهای طولانی را به‌صورت دستی اجرا کنیم، Workflow پروژه دشوار می‌شود.

آیا package.json می‌تواند این عملیات را نیز مدیریت کند؟

پاسخ، Scripts است.

Scripts

در package.json می‌توانیم Commandهای متداول پروژه را به‌عنوان Script تعریف کنیم.

برای مثال:

"scripts": {
"start": "node server.js"
}

پس به‌جای اینکه هر بار Command اصلی را مستقیماً وارد کنیم، می‌توانیم Script تعریف‌شده را اجرا کنیم.

مثلاً:

npm run start

در اینجا npm نقش اجراکنندهٔ Script را نیز بر عهده دارد.

این موضوع در پروژه‌های واقعی اهمیت زیادی دارد، زیرا عملیات تکراری پروژه را می‌توان با نام‌های مشخص و قابل پیش‌بینی در اختیار اعضای تیم قرار داد.

به‌این‌ترتیب، package.json فقط فهرست Dependencyها نیست.

این فایل به تدریج به یک نقطهٔ مرکزی برای تعریف بخشی از Workflow پروژه تبدیل می‌شود.

اکنون رابطهٔ مفاهیم اصلی فصل را می‌توانیم بهتر ببینیم:

↓

↓

↓
project operations

اما اینجا یک نکتهٔ مهم وجود دارد.

Package Management فقط نصب یک Package نیست.

اگر فقط یک Package را نصب کنیم، بخشی از مسئله را حل کرده‌ایم.

مدیریت واقعی Dependencyها شامل مجموعه‌ای از تصمیم‌ها و عملیات مرتبط با آن‌هاست.

Package Management

Package Management یعنی مدیریت چرخهٔ استفاده از Packageها در یک پروژه.

این چرخه می‌تواند شامل مواردی مانند موارد زیر باشد:

Discover
↓
Install
↓
Record
↓
Version
↓
Update
↓

npm این عملیات را برای پروژه ساده‌تر می‌کند و package.json اطلاعات مورد نیاز پروژه را ثبت می‌کند.

در نتیجه، یک پروژهٔ JavaScript می‌تواند به شکلی قابل پیش‌بینی Dependencyهای خود را تعریف و مدیریت کند.

این موضوع در یک پروژهٔ تیمی اهمیت بیشتری پیدا می‌کند.

فرض کنید پروژهٔ شما روی سیستم شما به چند Package وابسته است.

اگر Dependencyها به‌صورت مشخص ثبت نشده باشند، توسعه‌دهندهٔ دیگری که پروژه را دریافت می‌کند نمی‌داند چه چیزی باید نصب شود.

اما اگر Dependencyها در package.json تعریف شده باشند، پروژه می‌تواند نیازمندی‌های خود را به‌صورت صریح اعلام کند.

بنابراین:

package.json تعریف می‌کند پروژه به چه چیزهایی نیاز دارد و npm ابزار انجام بسیاری از عملیات مربوط به آن نیازمندی‌هاست.

این تفاوت مهم است.

package.json خودش Package را نصب نمی‌کند.

npm نیز جای package.json را نمی‌گیرد.

این دو در کنار یکدیگر کار می‌کنند.

یک Workflow واقعی

اکنون یک پروژهٔ ساده را از ابتدا تا مدیریت Dependency آن دنبال کنیم.

فرض کنید یک JavaScript Project داریم که برای یکی از قابلیت‌های خود به یک Package خارجی نیاز دارد.

اولین مسئله این است که Package مورد نیاز را پیدا کنیم.

Package در یک Registry منتشر شده است.

برای دریافت آن از npm استفاده می‌کنیم.

npm Package را دریافت می‌کند و اطلاعات Dependency را در package.json ثبت می‌کند.

از این لحظه پروژه دیگر فقط شامل Source Code خودمان نیست.

ساختار مفهومی پروژه به شکل زیر درمی‌آید:

Project
├── Source Code
├── package.json
└── Dependencies

اکنون اگر Dependency مورد نظر Version مشخصی داشته باشد، آن Version نیز در تعریف Dependency ثبت می‌شود.

اگر پروژه عملیات تکراری داشته باشد، می‌توانیم Commandهای مورد نیاز را نیز به‌عنوان Scripts تعریف کنیم.

در نتیجه، package.json اطلاعات مهمی دربارهٔ ساختار و نیازمندی‌های پروژه در اختیار ما قرار می‌دهد.

این همان چیزی است که یک پروژهٔ JavaScript را از مجموعه‌ای از فایل‌های مستقل به یک Project قابل مدیریت نزدیک می‌کند.

Best Practices
Dependencyها را آگاهانه اضافه کنید

هر Package جدید بخشی از Dependencyهای پروژه می‌شود.

بنابراین فقط زمانی Package اضافه کنید که واقعاً نیاز پروژه را برطرف کند.

Versionها را درک کنید

وجود یک Version در package.json به این معنا نیست که فقط نام Package اهمیت دارد.

باید بدانیم پروژه چه محدوده‌ای از Versionها را می‌پذیرد و تغییر Version چه اثری می‌تواند داشته باشد.

package.json را بخشی از Project Definition بدانید

این فایل را صرفاً یک فایل تنظیماتی در نظر نگیرید.

package.json بخشی از تعریف پروژه و نیازمندی‌های آن است.

Scripts را برای عملیات تکراری استفاده کنید

اگر اعضای تیم باید دائماً یک Command مشخص را اجرا کنند، بهتر است آن عملیات به‌صورت Script تعریف شود.

این کار Workflow پروژه را قابل پیش‌بینی‌تر می‌کند.

Dependencyهای غیرضروری اضافه نکنید

هر Dependency جدید، بخشی از پیچیدگی پروژه را افزایش می‌دهد.

استفاده از Package باید دلیل مشخصی داشته باشد.

Common Mistakes
اشتباه اول: یکی دانستن npm و Package

npm یک Package نیست.

npm ابزاری برای مدیریت Packageها و اجرای عملیات مرتبط با آن‌هاست.

اشتباه دوم: یکی دانستن Package و Dependency

هر Dependency یک Package مورد نیاز پروژه است، اما مفهوم Package به خودی خود به معنای Dependency بودن نیست.

Package می‌تواند به‌صورت مستقل منتشر شود؛ زمانی که پروژه به آن وابسته می‌شود، در نقش Dependency قرار می‌گیرد.

اشتباه سوم: تصور اینکه package.json خودش Dependencyها را نصب می‌کند

package.json نیازمندی‌های پروژه را توصیف می‌کند.

ابزاری مانند npm این اطلاعات را برای انجام عملیات Package Management استفاده می‌کند.

اشتباه چهارم: نادیده گرفتن Version

نوشتن نام Dependency بدون توجه به Version آن، دید کاملی نسبت به Dependency Management ایجاد نمی‌کند.

Version تعیین می‌کند پروژه نسبت به تغییرات Dependency چه محدوده‌ای از نسخه‌ها را می‌پذیرد.

اشتباه پنجم: استفاده از Package برای هر مسئلهٔ کوچک

Packageها می‌توانند توسعه را سریع‌تر کنند، اما اضافه کردن Dependencyهای زیاد نیز هزینه و پیچیدگی ایجاد می‌کند.

مسئله باید ابتدا فهمیده شود و سپس مشخص شود آیا استفاده از یک Package راه‌حل مناسبی است یا خیر.

Summary

در یک JavaScript Project معمولاً لازم نیست همهٔ قابلیت‌ها را از ابتدا خودمان پیاده‌سازی کنیم.

کدی که قابلیت استفادهٔ مجدد و توزیع دارد می‌تواند به شکل یک Package منتشر شود.

Packageها در Registry قرار می‌گیرند و توسعه‌دهندگان می‌توانند آن‌ها را از طریق ابزارهایی مانند npm دریافت و مدیریت کنند.

اما یک پروژه باید بتواند نیازمندی‌های خود را به‌صورت مشخص اعلام کند.

این وظیفه تا حد زیادی بر عهدهٔ package.json است.

وقتی پروژه به یک Package نیاز داشته باشد، آن Package به‌عنوان Dependency پروژه شناخته می‌شود.

از آنجا که Dependencyها در طول زمان تغییر می‌کنند، Versioning اهمیت پیدا می‌کند.

از طرف دیگر، پروژه عملیات تکراری مختلفی دارد که می‌توان آن‌ها را با Scripts مدیریت کرد.

Technical Interview
Junior-Level
سؤال 1: Package چیست؟

پاسخ:

Package یک واحد قابل توزیع از کد و اطلاعات مرتبط است که می‌تواند در پروژه‌های دیگر استفاده شود.

سؤال 2: npm چیست؟

پاسخ:

npm یک Package Manager و بخشی از اکوسیستم JavaScript است که برای نصب، مدیریت و اجرای عملیات مرتبط با Packageها استفاده می‌شود.

سؤال 3: package.json چه نقشی دارد؟

پاسخ:

package.json اطلاعات اصلی پروژه، Dependencyها، Versionهای آن‌ها و Scripts پروژه را توصیف می‌کند.

سؤال 4: Dependency چیست؟

پاسخ:

Dependency یک Package خارجی است که پروژه برای ارائهٔ قابلیت‌های خود به آن نیاز دارد.

Mid-Level
سؤال 5: تفاوت npm و package.json چیست؟

پاسخ:

package.json نیازمندی‌ها و بخشی از مشخصات پروژه را تعریف می‌کند، در حالی که npm ابزاری است که برای مدیریت Packageها و اجرای عملیات مرتبط با آن‌ها استفاده می‌شود.

سؤال 6: چرا Versioning برای Dependencyها مهم است؟

پاسخ:

چون Packageها در طول زمان تغییر می‌کنند و پروژه باید بتواند مشخص کند چه Version یا چه محدوده‌ای از Versionها را می‌پذیرد تا تغییرات Dependency رفتار پروژه را به‌صورت کنترل‌نشده تغییر ندهد.

سؤال 7: چرا Scripts در package.json قرار می‌گیرند؟

پاسخ:

برای تعریف و استانداردسازی Commandهای تکراری پروژه تا اعضای تیم بتوانند عملیات رایج را با Commandهای مشخص و قابل پیش‌بینی اجرا کنند.

Senior-Level
سؤال 8: چرا Dependency Management بخشی از مهندسی پروژه محسوب می‌شود؟

پاسخ:

زیرا Dependencyها مستقیماً روی قابلیت‌های پروژه، Versionهای مورد استفاده، قابلیت بازتولید محیط توسعه و Workflow تیم اثر می‌گذارند. بنابراین مدیریت آن‌ها فقط یک عملیات نصب Package نیست، بلکه بخشی از مدیریت ساختار و نیازمندی‌های پروژه است.

سؤال 9: چرا اضافه کردن Dependency جدید یک تصمیم مهندسی است؟

پاسخ:

چون هر Dependency جدید پیچیدگی، وابستگی و هزینهٔ نگهداری پروژه را افزایش می‌دهد. بنابراین باید مشخص باشد که Package چه مسئله‌ای را حل می‌کند و آیا ارزش آن نسبت به هزینهٔ اضافه‌شدن به پروژه منطقی است یا خیر.

سؤال 10: رابطهٔ Package، npm و package.json چیست؟

پاسخ:

Package واحد قابل توزیع کد است، Registry محل انتشار و دریافت آن است، npm ابزار مدیریت این Packageهاست و package.json نیازمندی‌ها و اطلاعات مربوط به Packageهای مورد استفادهٔ پروژه را ثبت می‌کند.

Golden Answers

Package چیست؟

Package یک واحد قابل توزیع و قابل استفادهٔ مجدد از کد و اطلاعات مرتبط است.

npm چیست؟

npm ابزار مدیریت Packageها در اکوسیستم JavaScript است.

Dependency چیست؟

Dependency یک Package خارجی است که پروژه برای ارائهٔ قابلیت‌های خود به آن نیاز دارد.

package.json چیست؟

package.json فایل توصیف پروژه است که اطلاعاتی مانند Dependencyها، Versionها و Scripts را ثبت می‌کند.

چرا Versioning مهم است؟

چون Dependencyها تغییر می‌کنند و پروژه باید بتواند محدودهٔ Versionهای قابل قبول خود را کنترل کند.

Package Management چیست؟

Package Management فرآیند مدیریت Packageها و Dependencyهای مورد استفادهٔ پروژه از مرحلهٔ دریافت و ثبت تا کنترل Version و عملیات مرتبط با آن‌هاست.

Conclusion

در ابتدای فصل، مسئله ساده بود:

پروژه به کدی نیاز دارد که خودش آن را ننوشته است.

این نیاز ما را به Package رساند.

برای پیدا کردن و دریافت Package به Registry نیاز داشتیم.

برای مدیریت ارتباط با Registry و Packageها به npm رسیدیم.

بعد مشخص شد که پروژه باید نیازمندی‌های خود را ثبت کند؛ بنابراین package.json وارد جریان شد.

وقتی Package به نیاز پروژه تبدیل شد، مفهوم Dependency شکل گرفت.

اما Dependencyها ثابت نیستند و تغییر می‌کنند؛ بنابراین به Versioning نیاز پیدا کردیم.

در نهایت، پروژه فقط Dependency ندارد؛ بلکه عملیات تکراری نیز دارد که می‌توان با Scripts آن‌ها را مدیریت کرد.

بنابراین مسئلهٔ اولیه به یک سیستم کامل‌تر تبدیل شد:

npm
↓
package.json
↓

↓

↓

↓
Package Management

اما اکنون یک سؤال مهم‌تر باقی می‌ماند.

تا اینجا یاد گرفتیم چگونه Dependencyهای پروژه را تعریف و مدیریت کنیم.

اما وقتی Source Code، Moduleها و Dependencyهای یک پروژه در کنار هم قرار می‌گیرند، چگونه این کد برای اجرای نهایی در محیط Development یا Production آماده می‌شود؟

پاسخ این سؤال ما را به Build Process می‌رساند.
