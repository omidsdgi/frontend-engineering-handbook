تا اینجا، مفاهیم JavaScript را از Fundamentals زبان تا Functions، Objects، Modules و برنامه‌نویسی Asynchronous بررسی کرده‌ایم. با این دانش می‌توانیم منطق یک Application را پیاده‌سازی کنیم؛ اما نوشتن کد صحیح به‌تنهایی برای تحویل یک نرم‌افزار قابل اعتماد کافی نیست.

فرض کنید در حال توسعه یک Recipe Application هستیم. این برنامه اطلاعات دستورهای غذایی را از یک API دریافت می‌کند، نتایج جستجو را نمایش می‌دهد و امکان مشاهده جزئیات هر Recipe را فراهم می‌کند.

در ابتدای کار، ممکن است چند فایل JavaScript برای دریافت اطلاعات و نمایش نتایج کافی باشند. اما با افزایش قابلیت‌ها، تعداد فایل‌ها و Dependencyها بیشتر می‌شود. هم‌زمان، احتمال خطاهای منطقی، ناسازگاری در سبک کدنویسی و مشکلات مربوط به آماده‌سازی برنامه برای انتشار نیز افزایش می‌یابد.

در چنین شرایطی، یک سؤال مهم مطرح می‌شود: آیا کافی است کد را بنویسیم، در مرورگر اجرا کنیم و پس از اطمینان از ظاهر مناسب رابط کاربری آن را منتشر کنیم؟

خیر. هرکدام از این مراحل فقط بخشی از فرایند توسعه را پوشش می‌دهند. اجرای موفق برنامه لزوماً به معنای نبود خطا نیست؛ همان‌طور که کد خوانا لزوماً عملکرد صحیح را تضمین نمی‌کند. همچنین، کدی که در محیط توسعه به‌درستی اجرا می‌شود، ممکن است هنوز برای انتشار آماده نباشد.

Development Workflow مجموعه‌ای از مراحل و بررسی‌های مرتبط است که کد را از مرحله توسعه به مرحله آماده‌سازی و انتشار می‌رساند. هدف این Workflow آن است که کیفیت کد، صحت عملکرد و آمادگی پروژه برای اجرا در محیط Production به‌صورت منظم بررسی شوند.

بنابراین، مسئله اصلی فقط انتخاب ابزارهای مناسب نیست. ابتدا باید بدانیم هر مرحله چه مسئله‌ای را حل می‌کند، چرا به مرحله بعد نیاز داریم و چگونه می‌توانیم این مراحل را به یک فرایند قابل تکرار تبدیل کنیم.

از Project به Source Code

یک JavaScript Project را نباید صرفاً مجموعه‌ای از فایل‌های کد در نظر بگیریم. پروژه، محیط سازمان‌یافته‌ای است که Source Code، تنظیمات، Dependencyها و ابزارهای موردنیاز برای توسعه و اجرای برنامه را در کنار یکدیگر قرار می‌دهد.

این تمایز اهمیت دارد؛ زیرا یک فایل JavaScript ممکن است به‌تنهایی قابل اجرا باشد، اما یک Application واقعی معمولاً از چندین فایل و قابلیت مرتبط تشکیل می‌شود. برای مثال، بخش جستجوی Recipe می‌تواند مسئول دریافت ورودی کاربر باشد، بخشی دیگر اطلاعات را از API دریافت کند و بخش دیگری نتایج را نمایش دهد.

در این وضعیت، Source Code به مجموعه فایل‌هایی گفته می‌شود که منطق و رفتار موردنظر Application در آن‌ها پیاده‌سازی شده است. این کدها مبنای اصلی توسعه هستند و برنامه‌نویس معمولاً هنگام افزودن قابلیت‌ها یا رفع خطاها، آن‌ها را تغییر می‌دهد.

اما Source Code زمانی به‌خوبی قابل مدیریت است که ارتباط میان بخش‌های مختلف آن مشخص باشد. اگر تمام مسئولیت‌ها در یک فایل بزرگ قرار گیرند، یافتن محل یک خطا، تغییر یک قابلیت و بررسی تأثیر آن بر بخش‌های دیگر دشوارتر می‌شود.

به همین دلیل، با رشد Application، مسئله فقط افزایش تعداد خطوط کد نیست؛ بلکه مدیریت وابستگی‌ها و ارتباط میان بخش‌های مختلف نیز اهمیت پیدا می‌کند.

Modules و سازمان‌دهی کد

برای مدیریت بهتر Source Code، می‌توانیم کدهای مرتبط را در Moduleهای جداگانه قرار دهیم. هر Module مرز مشخصی برای بخشی از کد ایجاد می‌کند و امکان می‌دهد قابلیت‌های موردنیاز از طریق import و export میان فایل‌ها به اشتراک گذاشته شوند.

برای مثال، در Recipe Application می‌توان مسئولیت دریافت اطلاعات را از مسئولیت نمایش نتایج جدا کرد. Module مربوط به دریافت اطلاعات می‌تواند تابع موردنیاز را صادر کند و Module دیگری آن را وارد کرده و به کار بگیرد.

// recipeService.js
export async function getRecipe(id) {
const response = await fetch(`/api/recipes/${id}`);

if (!response.ok) {
throw new Error('Failed to fetch recipe');
}

return response.json();
}
// recipeController.js
import { getRecipe } from './recipeService.js';

در این مثال، Module دوم به‌جای تعریف دوباره منطق دریافت اطلاعات، از قابلیت موجود در Module اول استفاده می‌کند.

نکته اصلی این نیست که هر قابلیت الزاماً باید در یک فایل مستقل قرار گیرد. هدف، مشخص‌کردن مسئولیت‌ها و ایجاد مرزهایی است که تغییر و بررسی کد را آسان‌تر کنند.

با این حال، جداسازی فایل‌ها به‌تنهایی تمام مشکلات را حل نمی‌کند. یک Module ممکن است به Module دیگری وابسته باشد و آن Module نیز برای اجرای صحیح به قابلیت دیگری نیاز داشته باشد. بنابراین، با افزایش تعداد Moduleها، مسئله بعدی مشخص می‌شود: چگونه وابستگی‌های پروژه را مدیریت کنیم؟

Dependencies و قابلیت تکرارپذیری پروژه

در یک Application واقعی، معمولاً همه قابلیت‌ها را از ابتدا پیاده‌سازی نمی‌کنیم. ممکن است برای تست، بررسی کیفیت کد یا آماده‌سازی فایل‌ها برای انتشار، از ابزارها و کتابخانه‌های موجود استفاده کنیم.

به هر کتابخانه یا ابزار خارجی که پروژه برای بخشی از کار خود به آن وابسته است، Dependency گفته می‌شود.

برای مثال، یک پروژه ممکن است از کتابخانه‌ای برای تست، ابزاری برای بررسی خطاهای رایج کد و ابزاری دیگر برای تبدیل و آماده‌سازی فایل‌ها استفاده کند.

این وابستگی‌ها باید به شکلی مدیریت شوند که پروژه فقط روی رایانه توسعه‌دهنده فعلی قابل استفاده نباشد. اگر توسعه‌دهنده دیگری پروژه را دریافت کند، باید بتواند وابستگی‌های موردنیاز را شناسایی و محیط توسعه را با نسخه‌های سازگار آماده کند.

در پروژه‌های JavaScript، فایل package.json اطلاعاتی درباره پروژه، Dependencyها و Scriptهای قابل اجرا نگه می‌دارد. Package Managerهایی مانند npm از این اطلاعات برای مدیریت بسته‌ها و اجرای دستورهای تعریف‌شده استفاده می‌کنند.

برای مثال، ممکن است در package.json چنین Scriptهایی داشته باشیم:

{
"scripts": {
"lint": "eslint .",
"format": "prettier . --write",
"test": "vitest run",
"build": "vite build"
}
}

این Scriptها نمونه‌ای از نحوه تعریف فرمان‌های متداول پروژه هستند. ابزارهای استفاده‌شده باید از قبل در پروژه نصب و متناسب با ساختار آن پیکربندی شده باشند.

با این روش، به‌جای آنکه هر توسعه‌دهنده دستورهای متفاوتی را به خاطر بسپارد، می‌توانیم عملیات متداول را از طریق یک رابط مشخص اجرا کنیم.

البته وجود package.json به‌تنهایی تضمین نمی‌کند که دو محیط دقیقاً یکسان باشند. نسخه Package Manager، فایل Lock و محیط اجرا نیز می‌توانند در تکرارپذیری نتیجه مؤثر باشند. جزئیات مدیریت بسته‌ها و نسخه‌ها موضوع فصل مستقل خود است.

تا اینجا، پروژه ساختار مشخصی دارد و وابستگی‌های آن نیز قابل مدیریت هستند. با این حال، هنوز نمی‌دانیم کد نوشته‌شده تا چه اندازه از نظر کیفیت و سازگاری با قواعد پروژه قابل قبول است. برای پاسخ به این سؤال، به بررسی خودکار Source Code نیاز داریم.

Linting و کشف مشکلات کد

وقتی یک پروژه بزرگ‌تر می‌شود، بررسی دستی تمام فایل‌ها برای پیدا کردن مشکلات احتمالی دشوارتر خواهد شد. علاوه بر این، بعضی خطاها از روی ظاهر کد به‌راحتی تشخیص داده نمی‌شوند و ممکن است تا زمان اجرای یک مسیر خاص از برنامه پنهان بمانند.

Linting فرایند بررسی Source Code بر اساس مجموعه‌ای از قواعد است. ابزاری مانند ESLint می‌تواند الگوهای مشکوک، برخی خطاهای رایج و تخلف از قواعد تعریف‌شده برای پروژه را شناسایی کند.

برای مثال، فرض کنید در یک بخش از برنامه متغیری تعریف شده است که هرگز استفاده نمی‌شود، یا نام متغیری با نام دیگری که در همان Scope وجود دارد اشتباه گرفته شده است. بسته به قواعد و تنظیمات فعال، ابزار Lint می‌تواند چنین مواردی را گزارش کند.

هدف این ابزار فقط زیباترکردن کد نیست. بعضی از قواعد مستقیماً به جلوگیری از خطاهای برنامه‌نویسی کمک می‌کنند؛ در حالی که برخی دیگر برای حفظ قراردادهای کدنویسی تیم در نظر گرفته شده‌اند.

با این حال، باید میان گزارش یک ابزار و اثبات صحت برنامه تفاوت قائل شویم. اگر Linter هیچ هشداری ندهد، نمی‌توان نتیجه گرفت که برنامه از نظر منطق کسب‌وکار یا رفتار زمان اجرا کاملاً صحیح است. Linting تنها بخش مشخصی از کیفیت کد را بررسی می‌کند.

همچنین، Linter معمولاً تمام تصمیم‌های مربوط به ظاهر کد را بر عهده ندارد. ممکن است دو توسعه‌دهنده کدی بدون خطای Lint بنویسند، اما درباره طول خطوط، نحوه استفاده از نقل‌قول‌ها یا فاصله‌گذاری‌ها با یکدیگر تفاوت داشته باشند.

این مسئله ما را به مسئولیت دیگری در Workflow می‌رساند.

Formatting و یکسان‌سازی ظاهر کد

در یک تیم توسعه، حتی اگر همه اعضا منطق برنامه را به‌درستی پیاده‌سازی کنند، تفاوت در شیوه قالب‌بندی می‌تواند خواندن و مقایسه تغییرات را دشوار کند.

Formatting فرایند یکسان‌سازی شکل ظاهری کد بر اساس قواعد قالب‌بندی است. ابزاری مانند Prettier می‌تواند فاصله‌گذاری، شکست خطوط، نقل‌قول‌ها و سایر جنبه‌های ظاهری کد را به‌صورت خودکار تنظیم کند.

برای مثال، دو شکل زیر از نظر ظاهر متفاوت‌اند:

const recipe={title:"Pasta",time:25};
const recipe = {
title: 'Pasta',
time: 25,
};

در این مثال، Formatter می‌تواند کد را به شکل استانداردشده تبدیل کند. هدف، تغییر منطق برنامه نیست؛ بلکه کاهش اختلاف‌های ظاهری و افزایش خوانایی است.

تفاوت Linting و Formatting را باید بر اساس مسئولیت آن‌ها درک کنیم:

Linting بررسی می‌کند که کد با قواعد مشخص‌شده سازگار است و برخی الگوهای مشکل‌ساز را شناسایی می‌کند.

Formatting شکل ظاهری کد را به‌صورت خودکار یکسان می‌کند.

این دو ابزار می‌توانند مکمل یکدیگر باشند. برای مثال، می‌توانیم ابتدا کد را Format کنیم و سپس آن را با Linter بررسی کنیم؛ البته ترتیب دقیق به ابزارها و تنظیمات پروژه بستگی دارد.

در نتیجه، بخشی از بررسی کیفیت کد را می‌توانیم خودکار کنیم. اما حتی کدی که از نظر قواعد و قالب‌بندی قابل قبول است، ممکن است نتیجه مورد انتظار Application را تولید نکند. برای بررسی این موضوع باید رفتار برنامه را نیز ارزیابی کنیم.

Testing و Debugging؛ بررسی رفتار واقعی برنامه

تا اینجا بررسی کردیم که چگونه می‌توان Source Code را سازمان‌دهی کرد و برخی مشکلات آن را بدون بررسی دستی تمام جزئیات شناسایی کرد. اما هیچ‌یک از این اقدامات به‌تنهایی نشان نمی‌دهد که قابلیت‌های برنامه در شرایط مورد انتظار درست کار می‌کنند.

فرض کنید تابعی برای محاسبه زمان آماده‌سازی یک Recipe نوشته‌ایم. ممکن است کد آن از نظر قواعد Lint معتبر باشد، قالب‌بندی مناسبی داشته باشد و حتی بدون خطای Syntax اجرا شود؛ اما در صورت دریافت ورودی نامعتبر، نتیجه اشتباهی تولید کند.

برای بررسی چنین مسائلی به Testing نیاز داریم.

Testing به فرایند بررسی رفتار نرم‌افزار در برابر ورودی‌ها و شرایط مشخص گفته می‌شود. در تست، رفتار مورد انتظار را تعریف می‌کنیم و نتیجه واقعی برنامه را با آن مقایسه می‌کنیم.

برای مثال:

function calculateTotalTime(preparation, cooking) {
return preparation + cooking;
}

console.assert(calculateTotalTime(15, 30) === 45);

در این مثال، انتظار داریم مجموع زمان آماده‌سازی و پخت برابر با ۴۵ دقیقه باشد. console.assert() در صورت نادرست‌بودن شرط، اطلاعاتی برای بررسی ارائه می‌کند؛ اما این مثال صرفاً یک بررسی ساده است و جایگزین یک Test Suite ساختاریافته نیست.

در پروژه‌های واقعی، ابزارهایی مانند Vitest یا Jest امکان تعریف تست‌های مستقل، اجرای مجموعه تست‌ها و بررسی منظم رفتار توابع و بخش‌های مختلف برنامه را فراهم می‌کنند.

نکته مهم این است که تست باید یک رفتار معنادار را بررسی کند. صرفاً اجرای یک تابع یا بازکردن صفحه، بدون بررسی نتیجه مورد انتظار، تضمین مناسبی برای صحت عملکرد نیست.

Debugging در کنار Testing

اگر یک تست شکست بخورد، می‌دانیم که رفتار واقعی با انتظار ما مطابقت ندارد؛ اما هنوز علت آن را نمی‌دانیم. در این مرحله Debugging اهمیت پیدا می‌کند.

Debugging فرایند بررسی اجرای برنامه برای پیدا کردن علت یک مشکل است. توسعه‌دهنده می‌تواند مقدار متغیرها، مسیر اجرای کد و وضعیت بخش‌های مرتبط را بررسی کند تا مشخص شود خطا در کجا و به چه دلیل رخ داده است.

برای مثال، اگر تابع محاسبه زمان به‌جای 45 مقدار 1530 برگرداند، ممکن است یکی از ورودی‌ها به‌صورت String دریافت شده باشد و عملگر + به‌جای جمع عددی، الحاق رشته‌ای انجام دهد. بررسی مقدار واقعی ورودی‌ها به تشخیص علت کمک می‌کند.

Testing و Debugging دو مسئولیت متفاوت اما مرتبط دارند:

Testing مشخص می‌کند آیا رفتار برنامه با انتظار تعریف‌شده سازگار است.

Debugging به یافتن علت رفتار نادرست کمک می‌کند.

پس از اصلاح مشکل، اجرای مجدد تست مرتبط اهمیت دارد؛ زیرا تغییر کد ممکن است رفتارهای دیگری را نیز تحت تأثیر قرار دهد. در پروژه‌های بزرگ‌تر، مجموعه تست‌ها به ما کمک می‌کند اطمینان بیشتری داشته باشیم که اصلاح یک خطا باعث ایجاد خطای دیگری نشده است.

با وجود این، موفقیت تست‌ها نیز به معنای آماده‌بودن قطعی برنامه برای انتشار نیست. هنوز باید بررسی کنیم که کد چگونه برای محیط مقصد آماده می‌شود و آیا خروجی نهایی پروژه قابل اجرا و استقرار است یا خیر.

Build؛ تبدیل Source Code به خروجی قابل انتشار

تا این مرحله، Source Code را سازمان‌دهی کرده‌ایم، Dependencyها را مدیریت کرده‌ایم و ابزارهایی برای بررسی کیفیت و رفتار برنامه در اختیار داریم. اکنون باید به تفاوت میان کدی که توسعه‌دهنده روی آن کار می‌کند و خروجی موردنیاز برای اجرای برنامه در محیط مقصد توجه کنیم.

در پروژه‌های ساده JavaScript، ممکن است فایل‌های Source Code مستقیماً در مرورگر بارگذاری شوند و نیازی به یک Build Process مستقل نباشد. بنابراین، Build یک الزام مطلق برای تمام پروژه‌های JavaScript نیست.

اما در بسیاری از پروژه‌های مدرن، کد به چندین Module تقسیم شده و ممکن است از قابلیت‌هایی استفاده کند که برای محیط مقصد باید تبدیل یا بهینه‌سازی شوند. همچنین، بارگذاری تعداد زیادی فایل و انتقال کدهای غیرضروری می‌تواند بر نحوه توزیع و اجرای Application تأثیر بگذارد.

Build Process فرایندی است که Source Code و منابع موردنیاز پروژه را پردازش می‌کند و خروجی مناسب برای اجرای برنامه در محیط مقصد را تولید می‌کند.

بسته به ابزارها و نیازهای پروژه، این فرایند می‌تواند شامل مراحل زیر باشد:

Transformation: تبدیل کد یا منابع به شکلی که با نیازهای محیط مقصد سازگار باشد.

Bundling: ترکیب Moduleها و منابع مرتبط در یک یا چند فایل خروجی، در صورت نیاز.

Optimization: کاهش حجم خروجی یا حذف بخش‌های غیرضروری، در صورت امکان و پشتیبانی ابزار.

Production Build: تولید خروجی نهایی متناسب با تنظیمات محیط Production.

این مراحل الزاماً در تمام پروژه‌ها به همین ترتیب یا با همین ابزارها اجرا نمی‌شوند. برای مثال، ابزارهای مختلف ممکن است Transformation و Bundling را به شیوه‌های متفاوت انجام دهند یا برخی از این مراحل را در یک فرایند واحد ترکیب کنند.

برای درک بهتر، فرض کنید Recipe Application از چندین Module تشکیل شده است. در محیط توسعه، ابزارهای پروژه ممکن است فایل‌ها را به‌صورت جداگانه پردازش کنند تا تغییرات سریع‌تر قابل مشاهده باشند. هنگام Build، ابزار مربوطه می‌تواند وابستگی‌ها را پردازش کرده و فایل‌های خروجی لازم را برای انتشار آماده کند.

در اینجا باید یک تمایز مهم را در نظر بگیریم: Build کردن برنامه به معنای اثبات صحت آن نیست. Build موفق نشان می‌دهد فرایند Build توانسته است خروجی موردنیاز را تولید کند؛ اما به‌تنهایی تضمین نمی‌کند که تمام قابلیت‌های برنامه در زمان اجرا درست کار می‌کنند.

به همین دلیل، Build در کنار Linting، Testing و Debugging قرار می‌گیرد، نه به‌جای آن‌ها.

Production؛ از کد توسعه تا برنامه منتشرشده

پس از تولید خروجی مناسب، مرحله بعد آماده‌سازی و انتشار برنامه در محیط مقصد است. در توسعه وب، این محیط می‌تواند یک Web Server، یک سرویس Hosting یا زیرساختی باشد که فایل‌های Application را در اختیار کاربران قرار می‌دهد.

Production به محیطی اشاره دارد که نسخه منتشرشده نرم‌افزار برای استفاده واقعی در آن اجرا یا ارائه می‌شود.

محیط Development و Production اهداف یکسانی ندارند. در محیط توسعه، ابزارها معمولاً برای تسهیل تغییر کد، مشاهده خطاها و سرعت‌دادن به چرخه توسعه تنظیم می‌شوند. در مقابل، خروجی Production باید متناسب با نیازهای انتشار و اجرای برنامه آماده شده باشد.

برای مثال، یک پروژه مبتنی بر Vite می‌تواند با اجرای Script مربوط به build خروجی Production خود را تولید کند. این خروجی سپس، متناسب با نوع پروژه و زیرساخت انتخاب‌شده، در محیط Hosting مستقر می‌شود.

اما انتشار فقط کپی‌کردن فایل‌ها نیست. پیش از انتشار باید مطمئن شویم که خروجی موردنظر تولید شده، تنظیمات محیط مقصد مناسب هستند و منابع لازم در دسترس قرار دارند. پس از انتشار نیز بررسی عملکرد برنامه در محیط واقعی اهمیت دارد؛ زیرا تفاوت‌های محیطی می‌توانند مشکلاتی ایجاد کنند که در Development مشاهده نشده‌اند.

همچنین، اگر پروژه به API یا سرویس خارجی وابسته باشد، عملکرد نهایی آن فقط به JavaScript تولیدشده محدود نمی‌شود. در دسترس‌بودن سرویس‌ها، تنظیمات ارتباط و مجوزهای لازم نیز ممکن است بر رفتار Application تأثیر بگذارند. جزئیات استقرار و مدیریت زیرساخت از محدوده اصلی این فصل فراتر می‌روند؛ در اینجا هدف، درک جایگاه Production در Workflow است.

اکنون می‌توانیم مراحل فصل را به یک فرایند واحد متصل کنیم. Source Code سازمان‌یافته، Dependencyهای مدیریت‌شده، بررسی‌های خودکار و خروجی Build، هرکدام بخشی از آمادگی برنامه برای انتشار را فراهم می‌کنند. هیچ‌کدام به‌تنهایی کافی نیستند، اما در کنار یکدیگر Workflow قابل اعتمادتری می‌سازند.

یک Workflow عملی برای JavaScript Project

فرض کنید در Recipe Application قابلیت جدیدی برای نمایش زمان آماده‌سازی غذا اضافه کرده‌ایم. به‌جای اینکه تغییر را مستقیماً منتشر کنیم، می‌توانیم از یک Workflow مشخص استفاده کنیم.

تغییر Source Code: قابلیت جدید را در Module مسئول پیاده‌سازی آن اضافه می‌کنیم و از تغییرات غیرضروری در بخش‌های نامرتبط پرهیز می‌کنیم.

بررسی Dependencyها: مطمئن می‌شویم ابزارها و بسته‌های موردنیاز پروژه به‌درستی تعریف شده‌اند و تغییر جدید وابستگی پیش‌بینی‌نشده‌ای ایجاد نکرده است.

Linting و Formatting: کد را از نظر قواعد تعریف‌شده بررسی می‌کنیم و قالب‌بندی مورد انتظار پروژه را اعمال می‌کنیم.

Testing و Debugging: رفتار قابلیت جدید را با ورودی‌های مناسب بررسی می‌کنیم. اگر تستی شکست بخورد، علت را پیدا می‌کنیم، مشکل را اصلاح می‌کنیم و تست‌ها را دوباره اجرا می‌کنیم.

Build: خروجی متناسب با تنظیمات Production را تولید می‌کنیم و خطاهای احتمالی این مرحله را برطرف می‌کنیم.

Production: خروجی را در محیط مقصد منتشر می‌کنیم و رفتار قابلیت را پس از انتشار بررسی می‌کنیم.

این ترتیب یک الگوی عملی است، نه قانونی تغییرناپذیر. برای مثال، می‌توانیم تست‌ها را در چند مرحله از توسعه اجرا کنیم، نه فقط پیش از Build. همچنین، در پروژه‌های تیمی ممکن است بخشی از این بررسی‌ها به‌صورت خودکار در یک فرایند CI اجرا شوند.

نکته مهندسی مهم، حفظ ارتباط میان مراحل است. اگر تغییر کد انجام شده اما بررسی‌های لازم اجرا نشده‌اند، یا Build با موفقیت انجام شده ولی خروجی در محیط مقصد بررسی نشده است، بخشی از فرایند اعتبارسنجی ناقص مانده است.

هدف Workflow این نیست که تعداد بیشتری ابزار به پروژه اضافه کنیم. هدف این است که هر مرحله مسئله مشخصی را حل کند و نتیجه آن به مرحله بعد کمک کند.

Best Practices
۱. Workflow را قابل تکرار طراحی کنید

فرمان‌های رایج مانند Linting، Testing و Build باید به‌شکلی مشخص و مستند در دسترس باشند. Scriptهای package.json می‌توانند این کار را ساده‌تر کنند.

۲. Dependencyها را آگاهانه مدیریت کنید

وابستگی‌های پروژه باید مشخص باشند و Lockfile در صورت استفاده، متناسب با تغییرات Dependencyها نگهداری شود. این کار نصب مجدد و اجرای پروژه را قابل پیش‌بینی‌تر می‌کند.

۳. Linting و Formatting را با هم اشتباه نگیرید

یکسان‌سازی ظاهر کد با بررسی Ruleهای کدنویسی دو هدف متفاوت دارند. هرکدام باید نقش خود را در Workflow حفظ کنند.

۴. آزمون را به رفتار مورد انتظار مرتبط کنید

آزمون‌هایی ارزشمندند که رفتارهای مهم برنامه را بررسی کنند. صرفاً اجرای چند آزمون بدون توجه به شرایط و نتایج آن‌ها، تضمین قابل اعتمادی برای کیفیت ایجاد نمی‌کند.

۵. علت خطا را پیدا کنید، نه اینکه فقط نشانه آن را پنهان کنید

در Debugging، مسیر اجرای برنامه و مقادیر مهم را بررسی کنید. اصلاحی که بدون شناخت علت مشکل انجام شود، ممکن است مسئله اصلی را باقی بگذارد.

۶. موفقیت Build را با صحت برنامه یکی ندانید

Build موفق نشان می‌دهد خروجی موردنظر تولید شده است؛ نه اینکه تمام رفتارهای برنامه درست هستند. بررسی رفتار و خروجی باید همچنان بخشی از Workflow باشد.

۷. خروجی Production را بررسی کنید

نسخه نهایی باید در شرایط مناسب اجرا و بررسی شود. صرف تولید پوشه خروجی برای نتیجه‌گیری درباره آمادگی انتشار کافی نیست.

Common Mistakes
۱. تصور اینکه اجرای موفق برنامه در Development کافی است

برنامه ممکن است در محیط توسعه اجرا شود، اما هنگام Build یا استفاده در محیط مقصد با مشکل مواجه شود. هر مرحله بخشی متفاوت از وضعیت پروژه را بررسی می‌کند.

۲. تصور اینکه Linting تمام خطاها را پیدا می‌کند

Linter بر اساس Ruleهای تعریف‌شده کد را بررسی می‌کند. این ابزار نمی‌تواند صحت تمام منطق برنامه را تضمین کند؛ بنابراین Testing و Debugging همچنان ضروری‌اند.

۳. یکسان دانستن Formatting و Refactoring

Formatting ظاهر کد را مطابق قواعد مشخص تغییر می‌دهد. Refactoring با هدف بهبود ساختار داخلی کد، بدون تغییر رفتار مورد انتظار آن، انجام می‌شود. این دو فعالیت هدف یکسانی ندارند.

۴. تصور اینکه Build موفق یعنی برنامه آماده انتشار است

Build ممکن است موفق شود، اما خروجی همچنان دارای مشکل اجرایی یا رفتاری باشد. بررسی خروجی و شرایط استفاده واقعی نباید حذف شود.

۵. نادیده گرفتن Lockfile

مدیریت Dependencyها فقط ثبت نام Packageها نیست. نادیده گرفتن Lockfile در پروژه‌ای که از آن استفاده می‌کند، می‌تواند باعث تفاوت نسخه‌های نصب‌شده در محیط‌های مختلف شود.

۶. تبدیل Workflow به فهرستی از ابزارها

نصب ESLint، Prettier یا Parcel به‌تنهایی Workflow حرفه‌ای ایجاد نمی‌کند. مهم این است که بدانیم هر ابزار کدام مسئله را حل می‌کند و خروجی آن چگونه در تصمیم بعدی استفاده می‌شود.
Summary

Modern JavaScript Development Workflow فرایندی است که کد را از مرحله توسعه به مرحله آماده‌سازی و انتشار می‌رساند. اهمیت آن زمانی مشخص می‌شود که بدانیم نوشتن کد، بررسی کیفیت آن، ارزیابی رفتار برنامه و تولید خروجی قابل انتشار، مسئولیت‌های متفاوتی هستند.

ابتدا Project محیط سازمان‌یافته‌ای برای توسعه فراهم می‌کند و Source Code منطق برنامه را در خود جای می‌دهد. Modules به سازمان‌دهی کد کمک می‌کنند و Dependencies قابلیت‌ها و ابزارهای موردنیاز را در اختیار پروژه قرار می‌دهند.

سپس Linting برخی مشکلات کد را شناسایی می‌کند و Formatting ظاهر آن را یکسان می‌سازد. Testing رفتار برنامه را با انتظارات تعریف‌شده مقایسه می‌کند و Debugging به یافتن علت مشکلات کمک می‌کند.

در ادامه، Build Process خروجی موردنیاز برای محیط مقصد را تولید می‌کند و مرحله Production امکان انتشار و استفاده واقعی از برنامه را فراهم می‌سازد.

مدل ذهنی این فصل را می‌توان چنین خلاصه کرد:

Organized Source Code
↓
Managed Dependencies
↓
Code Quality Checks
↓
Behavior Verification
↓
Production Build
↓
Deployment and Verification

این مراحل به یکدیگر وابسته‌اند، اما هیچ‌کدام جایگزین کامل دیگری نیستند. یک Workflow مناسب، این مسئولیت‌ها را به شکلی قابل تکرار و متناسب با نیاز پروژه به هم متصل می‌کند.

Key Takeaways

Development Workflow مجموعه‌ای از فعالیت‌های مرتبط برای توسعه و آماده‌سازی نرم‌افزار است.

Source Code، Modules و Dependencies اجزای مرتبط یک JavaScript Project هستند.

Modules سازمان‌دهی Source Code را آسان‌تر می‌کنند، در حالی که Dependencies نیازهای خارجی پروژه را مشخص می‌کنند.

package.json و Lockfile نقش‌های متفاوتی در مدیریت وابستگی‌ها دارند.

Linting مشکلات احتمالی کد را بر اساس Ruleها بررسی می‌کند.

Formatting ظاهر کد را مطابق قواعد مشخص یکسان می‌کند.

Testing رفتار برنامه را با انتظار ما مقایسه می‌کند.

Debugging به شناسایی علت رفتار نادرست کمک می‌کند.

Build خروجی مناسب برای محیط مقصد تولید می‌کند.

Production محیط استفاده از نسخه منتشرشده برنامه است.

موفقیت یک مرحله، موفقیت تمام مراحل دیگر را تضمین نمی‌کند.

Workflow حرفه‌ای باید قابل تکرار، قابل بررسی و متناسب با نیازهای واقعی پروژه باشد.

فرایندی منظم از توسعه Source Code تا بررسی کیفیت، تست، Build و آماده‌سازی برنامه برای انتشار است.

۲. تفاوت Linting و Formatting چیست؟

Linting کد را بر اساس قواعد مشخص بررسی می‌کند و برخی مشکلات احتمالی را گزارش می‌دهد. Formatting ظاهر کد را مطابق قواعد قالب‌بندی یکسان می‌کند.

Mid-Level

۴. چرا مدیریت Dependencyها در Workflow اهمیت دارد؟

زیرا پروژه برای اجرا و توسعه به نسخه‌ها و قابلیت‌های مشخصی وابسته است. مدیریت صحیح این وابستگی‌ها، نصب و اجرای پروژه را قابل پیش‌بینی‌تر می‌کند.

۵. Testing و Debugging چه رابطه‌ای دارند؟

Testing مشخص می‌کند آیا رفتار واقعی با رفتار مورد انتظار سازگار است. Debugging به یافتن علت اختلاف کمک می‌کند تا بتوان مشکل را اصلاح کرد.

۶. چرا ممکن است برنامه در Development درست کار کند اما در Production با مشکل مواجه شود؟

زیرا محیط‌ها ممکن است از نظر تنظیمات، منابع در دسترس، نحوه پردازش کد یا ارتباط با سرویس‌های خارجی تفاوت داشته باشند. به همین دلیل، بررسی خروجی و رفتار برنامه در محیط مقصد ضروری است.

Senior Level

۷. چگونه می‌توان یک Workflow قابل اعتماد طراحی کرد؟

باید مسئولیت‌های توسعه، بررسی کیفیت، تست، Build و انتشار را مشخص کنیم؛ بررسی‌های قابل تکرار را خودکار سازیم و متناسب با ریسک و نیاز پروژه، کنترل‌های لازم را در هر مرحله قرار دهیم.

۸. آیا تمام پروژه‌های JavaScript به Bundling و Build Process نیاز دارند؟

خیر. پروژه‌های ساده ممکن است بدون Build Process مستقل اجرا شوند. نیاز به Bundling، Transformation و Optimization به ساختار Source Code، قابلیت‌های مورد استفاده و الزامات محیط مقصد بستگی دارد.

۹. چرا نمی‌توان Testing را به بررسی دستی رابط کاربری محدود کرد؟

زیرا بررسی دستی تمام ورودی‌ها، شرایط و مسیرهای اجرایی را تضمین نمی‌کند. تست‌های خودکار می‌توانند رفتارهای مشخص را به‌صورت تکرارپذیر بررسی کنند و احتمال بازگشت خطاهای قبلی را کاهش دهند.

Golden Answers
Junior — Development Workflow چیست؟

Development Workflow فرایندی قابل تکرار برای توسعه، بررسی و آماده‌سازی نرم‌افزار است. این فرایند می‌تواند شامل سازمان‌دهی کد، مدیریت Dependencyها، Linting، Formatting، Testing، Build و انتشار باشد. هدف آن افزایش قابلیت اعتماد و کاهش خطاهای فرایند توسعه است.

Mid-Level — تفاوت Linting، Testing و Build چیست؟

Linting کد را از نظر قواعد و برخی الگوهای مشکل‌ساز بررسی می‌کند. Testing رفتار برنامه را در برابر انتظارات مشخص ارزیابی می‌کند. Build نیز Source Code و منابع پروژه را، در صورت نیاز، پردازش می‌کند تا خروجی مناسب برای محیط مقصد تولید شود. این مراحل مسئولیت‌های متفاوتی دارند و جایگزین یکدیگر نیستند.

Senior — چه ویژگی‌هایی یک Workflow را قابل اعتماد می‌کند؟

یک Workflow قابل اعتماد، مراحل توسعه و انتشار را متناسب با ساختار پروژه تعریف می‌کند، بررسی‌های قابل تکرار را خودکار می‌سازد و میان اعتبارسنجی کد، تست رفتار و تولید خروجی تمایز قائل می‌شود. همچنین، موفقیت هر مرحله را به‌عنوان تضمین کامل مراحل بعدی در نظر نمی‌گیرد و رفتار برنامه را در محیط مقصد نیز بررسی می‌کند.

Conclusion

در این فصل دیدیم که توسعه یک JavaScript Application با نوشتن کد به پایان نمی‌رسد. کد باید سازمان‌دهی شود، وابستگی‌های آن مدیریت شوند، کیفیت و رفتار آن بررسی شود و در صورت نیاز، خروجی مناسبی برای محیط مقصد تولید کند.

هر مرحله بخشی از مسئله را حل می‌کند. Modules به سازمان‌دهی کد کمک می‌کنند، ابزارهای بررسی کیفیت مشکلات مشخصی را آشکار می‌سازند، تست‌ها رفتار برنامه را ارزیابی می‌کنند و Build Process خروجی لازم برای انتشار را آماده می‌کند.

با این حال، Workflow به ما می‌گوید چه مراحلی را طی کنیم و چه زمانی آن‌ها را بررسی کنیم؛ اما به‌تنهایی توضیح نمی‌دهد که با افزایش اندازه Application، مسئولیت‌های آن را چگونه سازمان‌دهی کنیم.

فرض کنید Recipe Application به‌تدریج قابلیت‌های بیشتری پیدا می‌کند. اکنون علاوه بر دریافت اطلاعات و نمایش Recipeها، بخش‌های جستجو، مدیریت State، اعتبارسنجی ورودی‌ها و ارتباط با API نیز به آن اضافه شده‌اند. حتی اگر Workflow مناسبی داشته باشیم، قرارگرفتن تمام این مسئولیت‌ها در یک بخش از برنامه، تغییر و نگهداری آن را دشوار می‌کند.

بنابراین، مسئله بعدی دیگر فقط بررسی و انتشار کد نیست؛ بلکه طراحی ساختار خود Application است.

چگونه یک JavaScript Script ساده را به Applicationی با مسئولیت‌های مشخص، وابستگی‌های قابل مدیریت و ساختاری قابل نگهداری تبدیل کنیم؟
