Core Question

چگونه JavaScript را در یک Workflow حرفه‌ای توسعه، بررسی و آماده انتشار کنیم؟

این فصل مفاهیم Modules، مدیریت Dependencies و Build را از ابتدا آموزش نمی‌دهد؛ این موضوعات در فصل‌های قبلی بررسی شده‌اند. هدف این است که نقش آن‌ها را در یک فرآیند منسجم توسعه نرم‌افزار درک کنیم.

مقدمه

تا اینجا با بخش‌های مختلف توسعه JavaScript آشنا شده‌ایم. می‌دانیم چگونه کد بنویسیم، آن را به Moduleهای مستقل تقسیم کنیم، Packageها را مدیریت کنیم و با ابزارهایی مانند Parcel و Babel فرآیند Build را انجام دهیم.

اما دانستن این مفاهیم به‌تنهایی تضمین نمی‌کند که بتوانیم یک پروژه قابل اعتماد و آماده انتشار تولید کنیم.

فرض کنید در حال توسعه یک Application برای مدیریت Recipeها هستیم. برنامه اطلاعات Recipe را دریافت می‌کند، آن‌ها را پردازش می‌کند و در رابط کاربری نمایش می‌دهد.

ممکن است کد در سیستم توسعه‌دهنده به‌درستی اجرا شود؛ اما هنگام بررسی آن، مشکلاتی مانند این موارد آشکار شوند:

یک Variable تعریف شده است اما استفاده نمی‌شود.

ساختار کد در فایل‌های مختلف ناهماهنگ است.

یک Function در شرایط خاص خروجی نادرست تولید می‌کند.

یک Dependency در سیستم دیگری به‌درستی نصب نمی‌شود.

نسخه نهایی برنامه با خطا Build می‌شود.

این مشکلات از جنس یکسانی نیستند. بعضی به کیفیت Source Code مربوط‌اند، بعضی به رفتار برنامه و بعضی به آماده‌سازی خروجی برای محیط انتشار.

بنابراین توسعه حرفه‌ای را نباید صرفاً نوشتن کد و اجرای آن دانست. به یک فرآیند نیاز داریم که در آن کد ایجاد شود، بررسی شود، رفتار آن آزمایش شود و سپس خروجی مناسب برای انتشار تولید گردد.

به چنین فرآیند منظمی Development Workflow گفته می‌شود.

Development Workflow چیست؟

Development Workflow مجموعه‌ای از مراحل و فعالیت‌های مرتبط است که توسعه‌دهنده برای ایجاد، بررسی، اصلاح و آماده‌سازی یک نرم‌افزار انجام می‌دهد.

هدف Workflow صرفاً افزایش سرعت توسعه نیست. یک Workflow مناسب کمک می‌کند خطاها زودتر شناسایی شوند، تغییرات قابل بررسی باشند و خروجی نهایی با اطمینان بیشتری آماده انتشار شود.

نکته مهم این است که Workflow یک فهرست ثابت از ابزارها نیست. ابزارها ممکن است تغییر کنند، اما نیازهای اصلی توسعه باقی می‌مانند:

کد باید ساختار مشخصی داشته باشد.

وابستگی‌های پروژه باید قابل مدیریت باشند.

کیفیت کد باید بررسی شود.

رفتار برنامه باید آزمایش شود.

خروجی نهایی باید برای محیط مقصد آماده باشد.

برای درک این فرآیند، ابتدا باید ببینیم Workflow از کجا آغاز می‌شود.

From Project to Source Code

هر Workflow با یک Project آغاز می‌شود؛ اما Project فقط مجموعه‌ای از فایل‌های JavaScript نیست.

یک JavaScript Project ممکن است شامل Source Code، Moduleها، فایل‌های تنظیمات، Dependencyها، Assetها و Scriptهایی باشد که عملیات توسعه و Build را مدیریت می‌کنند.

این اجزا با یکدیگر ارتباط دارند. بنابراین پیش از بررسی کیفیت کد، باید بدانیم چه چیزی را توسعه می‌دهیم و اجزای پروژه چگونه سازمان‌دهی شده‌اند.

برای مثال، در یک Recipe Application ممکن است ساختار زیر را داشته باشیم:

recipe-app/
├── src/
│   ├── model.js
│   ├── controller.js
│   └── views/
├── package.json
├── package-lock.json
└── index.html

این ساختار نمونه‌ای ساده است؛ ساختار واقعی هر پروژه می‌تواند متفاوت باشد.

نکته اصلی این است که فایل‌ها بر اساس نقش خود در پروژه قرار گرفته‌اند. Source Code در یک بخش نگهداری می‌شود و فایل‌های مربوط به مدیریت Packageها و تنظیمات در بخش دیگری قرار دارند.

چنین سازمان‌دهی‌ای به توسعه‌دهنده کمک می‌کند فایل موردنیاز را پیدا کند و تغییرات را در محدوده مناسب انجام دهد.

اما سازمان‌دهی فایل‌ها فقط نقطه شروع است. برای اینکه پروژه قابل نگهداری باقی بماند، خود Source Code نیز باید ساختار مناسبی داشته باشد.

چرا Source Code باید به Moduleها تقسیم شود؟

فرض کنید تمام مسئولیت‌های Application در یک فایل قرار گرفته باشند: دریافت اطلاعات از API، پردازش داده‌ها، مدیریت رویدادها و نمایش نتیجه.

در یک برنامه کوچک ممکن است چنین ساختاری قابل مدیریت باشد. اما با افزایش قابلیت‌ها، تغییر یک قسمت می‌تواند بررسی قسمت‌های دیگر را دشوار کند.

Moduleها کمک می‌کنند کد بر اساس مسئولیت‌ها تقسیم شود. برای مثال، منطق دریافت داده‌ها می‌تواند از کد مربوط به نمایش آن‌ها جدا باشد.

این جداسازی دو نتیجه مهم دارد:

هر بخش محدوده مشخص‌تری برای تغییر و بررسی دارد.

ارتباط میان بخش‌ها قابل فهم‌تر می‌شود.

بنابراین Moduleها صرفاً راهی برای تقسیم فایل‌ها نیستند؛ آن‌ها بخشی از ساختار مهندسی پروژه‌اند.

البته داشتن چندین Module به‌تنهایی کیفیت را تضمین نمی‌کند. اگر وابستگی میان آن‌ها نامشخص باشد یا یک بخش مسئولیت‌های نامرتبط زیادی داشته باشد، پروژه همچنان می‌تواند پیچیده و دشوار برای نگهداری باشد.

در این فصل، وارد طراحی عمیق Architecture نمی‌شویم؛ این موضوع در فصل بعد بررسی خواهد شد. در اینجا Moduleها را به‌عنوان یکی از اجزای Workflow در نظر می‌گیریم.

Dependencies and Reproducibility

Source Code برای اجرا ممکن است به Packageها و ابزارهای خارجی نیاز داشته باشد. این نیازها در قالب Dependencies مدیریت می‌شوند.

برای مثال، پروژه ممکن است از Parcel برای Build یا از ابزار دیگری برای بررسی کیفیت کد استفاده کند.

در این حالت، اجرای پروژه فقط به وجود فایل‌های Source Code وابسته نیست. ابزارها و Packageهای موردنیاز نیز باید در دسترس باشند.

اینجا مسئله مهمی ایجاد می‌شود: چگونه مطمئن شویم پروژه در سیستم توسعه‌دهنده و در محیط دیگری با Dependencyهای مورد انتظار اجرا می‌شود؟

نقش package.json و Lockfile

فایل package.json اطلاعاتی مانند نام پروژه، Packageهای موردنیاز و Scriptهای قابل اجرا را نگهداری می‌کند.

در کنار آن، فایل Lock مانند package-lock.json نسخه‌های دقیق‌تری از Dependencyهای حل‌شده را ثبت می‌کند تا نصب مجدد وابستگی‌ها قابل پیش‌بینی‌تر باشد.

این دو فایل نقش یکسانی ندارند:

package.json وابستگی‌ها و تنظیمات پروژه را تعریف می‌کند.

Lockfile جزئیات نسخه‌های حل‌شده در درخت Dependencyها را ثبت می‌کند.

وقتی پروژه به مخزن کد منتقل می‌شود، نگهداری این اطلاعات کمک می‌کند توسعه‌دهنده دیگری بتواند Dependencyهای پروژه را با سازگاری بیشتری نصب کند.

برای مثال، در یک پروژه مبتنی بر npm معمولاً می‌توان از دستور زیر برای نصب وابستگی‌ها بر اساس Lockfile استفاده کرد:

npm ci

این دستور برای نصب قابل تکرار در محیط‌هایی مانند CI مناسب است. برخلاف npm install، در صورت ناسازگاری package.json با Lockfile به‌جای بازنویسی خودکار Lockfile خطا می‌دهد.

البته نصب قابل تکرار به‌معنای تضمین اجرای صحیح برنامه نیست. این کار فقط یکی از شرایط لازم برای داشتن محیط توسعه قابل پیش‌بینی است.

Scriptها و تبدیل Workflow به فرمان‌های قابل اجرا

اگر برای اجرای پروژه، بررسی کد و Build هر بار لازم باشد فرمان‌های مختلف را از حافظه تایپ کنیم، احتمال خطا و ناهماهنگی افزایش می‌یابد.

package.json اجازه می‌دهد عملیات رایج را در قالب Scriptهای نام‌گذاری‌شده تعریف کنیم.

برای نمونه:

{
"scripts": {
"dev": "parcel index.html",
"lint": "eslint src",
"format": "prettier --write src",
"build": "parcel build index.html"
}
}

این نمونه فرض می‌کند Parcel، ESLint و Prettier قبلاً به‌عنوان ابزارهای پروژه نصب و متناسب با آن تنظیم شده‌اند.

اکنون فرمان‌هایی مانند npm run lint و npm run build نام مشخصی برای عملیات مربوط به خود دارند.

مزیت اصلی این روش، صرفاً کوتاه‌تر شدن فرمان‌ها نیست. Scriptها به اعضای پروژه می‌گویند یک عملیات استاندارد چگونه باید اجرا شود.

با این حال، اجرای این Scriptها باید هدف مشخصی داشته باشد. ابتدا باید بتوانیم تفاوت مشکلات مربوط به کیفیت کد، قالب‌بندی و رفتار برنامه را تشخیص دهیم.

Linting and Formatting

کدی که از نظر Syntax معتبر است، لزوماً کد باکیفیتی نیست. ممکن است Variable بلااستفاده داشته باشد، الگویی مستعد خطا را به کار برده باشد یا از نظر قالب‌بندی با سایر فایل‌های پروژه هماهنگ نباشد.

برای رسیدگی به این مسائل، دو فعالیت متفاوت داریم: Linting و Formatting.

Linting: شناسایی مشکلات احتمالی کد

Linting فرآیند بررسی Source Code بر اساس مجموعه‌ای از Ruleهاست.

ابزاری مانند ESLint می‌تواند مواردی مانند Variableهای بلااستفاده یا برخی الگوهای مسئله‌ساز را شناسایی کند. نتیجه این بررسی کمک می‌کند مشکلات پیش از آنکه به خطای اجرایی یا مسئله نگهداری تبدیل شوند، آشکار شوند.

برای مثال:

function getRecipe(recipe) {
const recipeId = recipe.id;
const recipeName = recipe.name;

return recipeId;
}

در این مثال، recipeName تعریف شده اما استفاده نشده است. یک Rule مناسب در Linter می‌تواند این مورد را گزارش کند.

این هشدار الزاماً به‌معنای خرابی خروجی برنامه نیست؛ اما نشانه‌ای است که ارزش بررسی دارد. شاید Variable به‌اشتباه باقی مانده باشد یا بخشی از منطق فراموش شده باشد.

بنابراین وظیفه Linter صرفاً پیدا کردن خطاهای قطعی نیست. Linting می‌تواند الگوهایی را نیز آشکار کند که احتمال بروز خطا یا دشواری نگهداری را افزایش می‌دهند.

با این حال، Linting جایگزین اجرای برنامه و Testing نیست. یک کد ممکن است تمام Ruleهای Linter را رعایت کند و همچنان رفتار نادرستی داشته باشد.

Formatting: یکسان‌سازی ظاهر کد

حتی اگر چند توسعه‌دهنده منطق یکسانی بنویسند، ممکن است درباره فاصله‌ها، تورفتگی‌ها، کوتیشن‌ها و نحوه شکستن خطوط سلیقه‌های متفاوتی داشته باشند.

این تفاوت‌ها همیشه خطای فنی ایجاد نمی‌کنند؛ اما بررسی کد و تشخیص تغییرات واقعی را دشوارتر می‌کنند.

Formatting با اعمال قواعد مشخص، ظاهر کد را یکسان می‌کند.

برای مثال، Prettier می‌تواند بر اساس تنظیمات پروژه، فاصله‌گذاری و قالب‌بندی کد را به‌شکل خودکار تنظیم کند.

تفاوت اصلی این دو فعالیت را باید روشن نگه داریم:

Linting درباره رعایت Ruleهای کدنویسی و مشکلات احتمالی کد هشدار می‌دهد.

Formatting ظاهر و ساختار نوشتاری کد را مطابق قواعد تعیین‌شده یکسان می‌کند.

این دو فعالیت می‌توانند مکمل یکدیگر باشند، اما جایگزین هم نیستند.

یک فایل ممکن است کاملاً Format شده باشد، ولی منطق اشتباهی داشته باشد. همچنین ممکن است منطق یک Function درست باشد، اما Linter درباره یک Variable بلااستفاده هشدار دهد.

در یک Workflow مناسب، بررسی کد و قالب‌بندی به فعالیت‌هایی مشخص و تکرارپذیر تبدیل می‌شوند. با این حال، هنوز یک سؤال مهم باقی می‌ماند: آیا برنامه واقعاً همان رفتاری را دارد که انتظار داریم؟

Testing and Debugging

Linting و Formatting به بررسی Source Code کمک می‌کنند؛ اما برای اطمینان از رفتار برنامه کافی نیستند.

فرض کنید تابعی برای استخراج اطلاعات یک Recipe نوشته‌ایم. کد ممکن است از نظر Syntax معتبر باشد، هیچ هشدار Linting نداشته باشد و از نظر ظاهری نیز منظم باشد؛ اما در صورت نبودن یکی از فیلدهای ورودی، نتیجه نامناسبی تولید کند.

برای بررسی چنین مسئله‌ای باید رفتار برنامه را ارزیابی کنیم.

در این مرحله دو فعالیت مکمل وارد Workflow می‌شوند: Testing و Debugging.

Testing: بررسی رفتار مورد انتظار

Testing به ما کمک می‌کند بررسی کنیم برنامه در شرایط مشخص، نتیجه مورد انتظار را تولید می‌کند یا نه.

برای مثال، اگر تابعی شناسه Recipe را دریافت می‌کند، می‌توانیم بررسی کنیم که برای ورودی معتبر مقدار صحیحی برگرداند.

در یک پروژه واقعی، آزمون‌ها می‌توانند رفتارهای مهم را بررسی کنند؛ از جمله:

ورودی معتبر و خروجی مورد انتظار

ورودی ناقص یا نامعتبر

رفتار در شرایط مرزی

حفظ رفتار قبلی پس از تغییر کد

نکته مهم این است که Testing فقط برای یافتن خطاهای موجود نیست. آزمون‌ها می‌توانند مشخص کنند که تغییرات جدید، قابلیت‌هایی را که قبلاً درست کار می‌کردند خراب نکرده‌اند.

برای مثال، اگر منطق استخراج Recipe تغییر کند، آزمون‌های موجود کمک می‌کنند رفتار مورد انتظار دوباره بررسی شود.

البته هیچ مجموعه آزمونی تضمین نمی‌کند که تمام خطاهای ممکن شناسایی شوند. ارزش Testing به کیفیت آزمون‌ها، شرایط بررسی‌شده و اهمیت رفتارهای پوشش‌داده‌شده بستگی دارد.

Debugging: پیدا کردن علت رفتار نادرست

وقتی یک آزمون شکست می‌خورد یا برنامه نتیجه نامنتظره‌ای تولید می‌کند، هنوز علت مشکل را نمی‌دانیم.

ممکن است داده ورودی اشتباه باشد، یک شرط درست عمل نکند یا یک Function مقدار نادرستی برگرداند.

Debugging فرآیند بررسی اجرای برنامه برای شناسایی علت خطاست.

در Debugging، توسعه‌دهنده به‌جای تغییر تصادفی کد، رفتار واقعی برنامه را مشاهده می‌کند، مقادیر مهم را بررسی می‌کند و مسیر اجرای منتهی به مشکل را دنبال می‌کند.

برای مثال، اگر یک Recipe در رابط کاربری نمایش داده نمی‌شود، باید مشخص کنیم مشکل در دریافت داده، پردازش آن یا مرحله نمایش رخ داده است. این کار به بررسی مرحله‌به‌مرحله جریان داده نیاز دارد، نه صرفاً تغییر کد تا زمانی که نتیجه ظاهراً درست شود.

تفاوت Testing و Debugging در هدف مستقیم آن‌هاست:

Testing بررسی می‌کند آیا رفتار برنامه با انتظار ما سازگار است.

Debugging کمک می‌کند علت رفتار نادرست را پیدا کنیم.

این دو فعالیت ارتباط نزدیکی دارند. یک آزمون ممکن است وجود مشکل را آشکار کند؛ سپس Debugging به شناسایی علت کمک می‌کند. پس از اصلاح کد نیز می‌توان آزمون را دوباره اجرا کرد تا نتیجه بررسی شود.

در نتیجه، توسعه فقط حرکت خطی از نوشتن کد به Build نیست. ممکن است در هر مرحله نیاز باشد به Source Code برگردیم، تغییر ایجاد کنیم و بررسی‌ها را تکرار کنیم.

Build: آماده‌سازی خروجی پروژه

پس از بررسی و اصلاح کد، باید آن را برای محیط مقصد آماده کنیم.

Source Code مورد استفاده در Development همیشه همان مجموعه فایل‌هایی نیست که باید در Production منتشر شوند. ممکن است پروژه از Moduleهای متعدد، Dependencyهای خارجی و Assetهای مختلف تشکیل شده باشد.

مرورگر یا محیط اجرای مقصد باید بتواند خروجی مناسب پروژه را دریافت کند. برای رسیدن به این هدف، از Build Process استفاده می‌کنیم.

Build می‌تواند فعالیت‌هایی مانند موارد زیر را انجام دهد:

پردازش Moduleها و Dependencyها

تبدیل Syntax در صورت نیاز به‌کمک ابزارهایی مانند Babel

ترکیب فایل‌ها و Assetها

بهینه‌سازی خروجی برای Production

جزئیات این عملیات به ابزار و تنظیمات پروژه بستگی دارد. در فصل‌های ۷۲ تا ۷۴، Build Process، Parcel و Babel به‌صورت مستقل بررسی شده‌اند؛ بنابراین در اینجا بر جایگاه Build در Workflow تمرکز می‌کنیم.

چرا Build باید پس از بررسی کد انجام شود؟

Build موفق نشان می‌دهد ابزار Build توانسته است خروجی موردنظر را تولید کند. اما این نتیجه به‌تنهایی اثبات نمی‌کند که برنامه از نظر منطقی درست کار می‌کند.

ممکن است Build بدون خطا انجام شود، ولی یک Function در شرایط خاص نتیجه اشتباهی تولید کند. از طرف دیگر، ممکن است کد از نظر منطقی درست باشد اما تنظیمات Build یا یک Dependency باعث شکست فرآیند شود.

به همین دلیل، بررسی کیفیت کد، Testing و Build پاسخگوی سؤال‌های متفاوتی هستند.

در یک Workflow مناسب، پیش از انتشار باید اطمینان حاصل کنیم که:

مشکلات قابل شناسایی کد بررسی شده‌اند.

رفتارهای مهم برنامه آزمایش شده‌اند.

فرآیند Build با موفقیت انجام شده است.

خروجی تولیدشده برای محیط مقصد بررسی شده است.

این مراحل به یکدیگر کمک می‌کنند، اما هیچ‌کدام جایگزین کامل دیگری نیست.

خروجی Build چه چیزی را تغییر می‌دهد؟

فرض کنید Source Code پروژه در پوشه src قرار دارد و Parcel برای تولید خروجی استفاده می‌شود.

در حالت Development، ابزار می‌تواند یک Development Server راه‌اندازی کند و تغییرات کد را برای توسعه‌دهنده در دسترس قرار دهد.

در حالت Production، هدف تولید خروجی مناسب برای انتشار است. بسته به تنظیمات ابزار، فایل‌های نهایی ممکن است در پوشه‌ای مانند dist قرار بگیرند.

پوشه dist در این مثال فقط یک نام متداول است؛ مسیر واقعی خروجی به تنظیمات Build Tool بستگی دارد.

نکته مهم، تفاوت میان Source Code و خروجی تولیدشده است. Source Code چیزی است که توسعه‌دهنده نگهداری و تغییر می‌دهد؛ خروجی Build چیزی است که برای اجرای برنامه در محیط مقصد آماده می‌شود.

Production: آماده‌سازی برای انتشار

پس از Build، پروژه می‌تواند برای انتشار آماده شود؛ اما تولید فایل‌های نهایی به‌تنهایی پایان Workflow نیست.

Production به محیطی اشاره دارد که نسخه منتشرشده برنامه در آن برای کاربران یا مصرف‌کنندگان واقعی در دسترس قرار می‌گیرد.

محیط Production با محیط Development هدف یکسانی ندارد.

در Development، توسعه‌دهنده به ابزارهایی برای تغییر سریع کد، مشاهده خطاها و بررسی رفتار برنامه نیاز دارد. در Production، تمرکز بر ارائه نسخه آماده استفاده است.

به همین دلیل، خروجی Production معمولاً از مسیر Build مشخصی تولید می‌شود و باید پیش از انتشار بررسی شود.

چه چیزی باید پیش از انتشار بررسی شود؟

فرض کنید Build با موفقیت انجام شده است. هنوز باید مطمئن شویم خروجی تولیدشده واقعاً قابل استفاده است.

برای یک JavaScript Application، بررسی‌های پایه می‌تواند شامل این موارد باشد:

فایل‌های لازم در خروجی Build وجود دارند.

مسیر Assetها و منابع موردنیاز صحیح است.

برنامه در محیط مقصد اجرا می‌شود.

قابلیت‌های اصلی برنامه رفتار مورد انتظار را دارند.

خطاهای مهمی که هنگام بررسی خروجی آشکار می‌شوند، رفع شده‌اند.

این بررسی اهمیت دارد، زیرا محیط واقعی ممکن است با محیط Development تفاوت داشته باشد. برای مثال، مسیر دسترسی به فایل‌ها یا نحوه ارائه Assetها می‌تواند در زمان انتشار با شرایط توسعه متفاوت باشد.

همچنین موفقیت Build به‌معنای موفقیت انتشار نیست. Build تولید خروجی را مدیریت می‌کند؛ انتشار یا Deployment، خروجی را در محیط مقصد در دسترس قرار می‌دهد.

این دو مفهوم به هم مرتبط‌اند، اما یکسان نیستند.

در این فصل، هدف بررسی عمیق سرویس‌های Hosting یا طراحی فرآیند Deployment نیست. نکته اصلی آن است که Workflow باید میان تولید خروجی و آماده بودن آن برای استفاده واقعی تمایز قائل شود.

یک Workflow یکپارچه در عمل

اکنون می‌توانیم مراحل فصل را در قالب یک فرآیند واقعی کنار هم قرار دهیم.

فرض کنید در حال توسعه یک Recipe Application هستیم و قابلیت جدیدی برای جستجوی Recipeها اضافه کرده‌ایم.

Workflow می‌تواند به این شکل پیش برود:

Project و Source Code: تغییر موردنیاز را در Module مربوط به جستجو پیاده‌سازی می‌کنیم.

Modules و Dependencies: بررسی می‌کنیم تغییر با ساختار Moduleها و Dependencyهای پروژه سازگار باشد.

Linting: کد را با Ruleهای تعیین‌شده بررسی می‌کنیم و مشکلات گزارش‌شده را ارزیابی می‌کنیم.

Formatting: قالب‌بندی را با قواعد پروژه یکسان می‌کنیم.

Testing و Debugging: رفتار جستجو را با ورودی‌های مناسب آزمایش می‌کنیم و در صورت مشاهده نتیجه نادرست، علت آن را پیدا می‌کنیم.

Build: خروجی Production را تولید می‌کنیم و مطمئن می‌شویم فرآیند Build موفق بوده است.

Production Readiness: خروجی را در شرایط مناسب بررسی می‌کنیم تا برای انتشار آماده باشد.

این ترتیب یک مسیر منطقی است، نه قانونی که هیچ‌گاه تغییر نمی‌کند. ممکن است در طول توسعه، برای اصلاح یک خطا به Source Code برگردیم یا پس از Build متوجه شویم که لازم است آزمون دیگری اضافه کنیم.

بنابراین Workflow حرفه‌ای هم ترتیب دارد و هم امکان بازگشت به مراحل قبلی را فراهم می‌کند.

نکته مهم‌تر این است که هر مرحله مسئله متفاوتی را بررسی می‌کند. اگر این تفاوت‌ها را درک کنیم، می‌توانیم تشخیص دهیم یک مشکل باید در کدام مرحله بررسی شود و از اتکا به یک ابزار یا بررسی واحد پرهیز کنیم.

Best Practices
۱. Workflow را قابل تکرار طراحی کنید

فرمان‌های رایج مانند Linting، Testing و Build باید به‌شکلی مشخص و مستند در دسترس باشند. Scriptهای package.json می‌توانند این کار را ساده‌تر کنند.

۲. Dependencyها را آگاهانه مدیریت کنید

وابستگی‌های پروژه باید مشخص باشند و Lockfile در صورت استفاده، متناسب با تغییرات Dependencyها نگهداری شود. این کار نصب مجدد و اجرای پروژه را قابل پیش‌بینی‌تر می‌کند.

۳. Linting و Formatting را با هم اشتباه نگیرید

یکسان‌سازی ظاهر کد با بررسی Ruleهای کدنویسی دو هدف متفاوت دارند. هرکدام باید نقش خود را در Workflow حفظ کنند.

۴. آزمون را به رفتار مورد انتظار مرتبط کنید

آزمون‌هایی ارزشمندند که رفتارهای مهم برنامه را بررسی کنند. صرفاً اجرای چند آزمون بدون توجه به شرایط و نتایج آن‌ها، تضمین قابل اعتمادی برای کیفیت ایجاد نمی‌کند.

۵. علت خطا را پیدا کنید، نه اینکه فقط نشانه آن را پنهان کنید

در Debugging، مسیر اجرای برنامه و مقادیر مهم را بررسی کنید. اصلاحی که بدون شناخت علت مشکل انجام شود، ممکن است مسئله اصلی را باقی بگذارد.

۶. موفقیت Build را با صحت برنامه یکی ندانید

Build موفق نشان می‌دهد خروجی موردنظر تولید شده است؛ نه اینکه تمام رفتارهای برنامه درست هستند. بررسی رفتار و خروجی باید همچنان بخشی از Workflow باشد.

۷. خروجی Production را بررسی کنید

نسخه نهایی باید در شرایط مناسب اجرا و بررسی شود. صرف تولید پوشه خروجی برای نتیجه‌گیری درباره آمادگی انتشار کافی نیست.

Common Mistakes
۱. تصور اینکه اجرای موفق برنامه در Development کافی است

برنامه ممکن است در محیط توسعه اجرا شود، اما هنگام Build یا استفاده در محیط مقصد با مشکل مواجه شود. هر مرحله بخشی متفاوت از وضعیت پروژه را بررسی می‌کند.

۲. تصور اینکه Linting تمام خطاها را پیدا می‌کند

Linter بر اساس Ruleهای تعریف‌شده کد را بررسی می‌کند. این ابزار نمی‌تواند صحت تمام منطق برنامه را تضمین کند؛ بنابراین Testing و Debugging همچنان ضروری‌اند.

۳. یکسان دانستن Formatting و Refactoring

Formatting ظاهر کد را مطابق قواعد مشخص تغییر می‌دهد. Refactoring با هدف بهبود ساختار داخلی کد، بدون تغییر رفتار مورد انتظار آن، انجام می‌شود. این دو فعالیت هدف یکسانی ندارند.

۴. تصور اینکه Build موفق یعنی برنامه آماده انتشار است

Build ممکن است موفق شود، اما خروجی همچنان دارای مشکل اجرایی یا رفتاری باشد. بررسی خروجی و شرایط استفاده واقعی نباید حذف شود.

۵. نادیده گرفتن Lockfile

مدیریت Dependencyها فقط ثبت نام Packageها نیست. نادیده گرفتن Lockfile در پروژه‌ای که از آن استفاده می‌کند، می‌تواند باعث تفاوت نسخه‌های نصب‌شده در محیط‌های مختلف شود.

۶. تبدیل Workflow به فهرستی از ابزارها

نصب ESLint، Prettier یا Parcel به‌تنهایی Workflow حرفه‌ای ایجاد نمی‌کند. مهم این است که بدانیم هر ابزار کدام مسئله را حل می‌کند و خروجی آن چگونه در تصمیم بعدی استفاده می‌شود.

Development Workflow فرآیندی منظم برای توسعه، بررسی و آماده‌سازی یک JavaScript Project است.

این فرآیند با شناخت Project و سازمان‌دهی Source Code آغاز می‌شود. Moduleها به تقسیم مسئولیت‌ها کمک می‌کنند و مدیریت Dependencyها امکان نصب و اجرای قابل پیش‌بینی‌تر پروژه را فراهم می‌کند.

سپس Linting و Formatting به بررسی کیفیت کد و یکسان‌سازی ظاهر آن کمک می‌کنند. Testing رفتار مورد انتظار برنامه را بررسی می‌کند و Debugging برای یافتن علت رفتار نادرست به کار می‌رود.

پس از بررسی و اصلاح کد، Build خروجی مناسب را تولید می‌کند. در نهایت، خروجی باید در شرایط مناسب بررسی شود تا برای Production و انتشار آماده باشد.

این مراحل هرکدام هدف مشخصی دارند. هیچ‌کدام به‌تنهایی کیفیت نهایی برنامه را تضمین نمی‌کنند. کیفیت Workflow از ارتباط درست میان این مراحل و توانایی توسعه‌دهنده در تشخیص مسئله مناسب در هر مرحله حاصل می‌شود.

۸. چرا Workflow باید قابل تکرار باشد؟

هرکدام مسئله متفاوتی را بررسی می‌کنند. Linting کد را بر اساس Ruleها تحلیل می‌کند، Testing رفتار برنامه را می‌آزماید و Build خروجی مناسب برای محیط مقصد تولید می‌کند. موفقیت در یک مرحله، نتیجه مراحل دیگر را تضمین نمی‌کند.

۱۰. اگر برنامه در Development درست کار کند اما در Production مشکل داشته باشد، چگونه باید مسئله را بررسی کرد؟

ابتدا باید شرایط اجرای Production، خروجی Build، مسیر Assetها و تفاوت‌های محیط مقصد بررسی شوند. سپس با مشاهده خطا و بازتولید آن، علت مشکل شناسایی می‌شود. تغییر تصادفی کد بدون مشخص کردن تفاوت میان دو محیط، روش قابل اعتمادی نیست.

۱۱. چه چیزی یک Workflow را حرفه‌ای می‌کند؟

قابلیت تکرار، روشن بودن مسئولیت هر مرحله، امکان شناسایی زودهنگام خطاها، بررسی رفتار برنامه و تولید خروجی قابل بررسی برای محیط مقصد. حرفه‌ای بودن به تعداد ابزارها وابسته نیست، بلکه به استفاده هدفمند از آن‌ها وابسته است.

۱۲. چرا باید خروجی Build را نیز بررسی کرد؟

زیرا Source Code و خروجی Build الزاماً ساختار یکسانی ندارند و ممکن است تفاوت‌های مربوط به پردازش فایل‌ها، مسیر منابع یا تنظیمات محیط مقصد فقط در خروجی نهایی آشکار شوند.

Golden Answers
Junior — Golden Answer

Development Workflow فرآیند منظم توسعه و بررسی یک پروژه است. در این فرآیند، کد سازمان‌دهی می‌شود، Dependencyها مدیریت می‌شوند، کیفیت و رفتار برنامه بررسی می‌شود و در نهایت خروجی مناسب برای انتشار تولید می‌شود.

Mid-Level — Golden Answer

در یک Workflow حرفه‌ای، Linting، Formatting، Testing، Debugging و Build مسئولیت‌های متفاوتی دارند. Linting مشکلات احتمالی کد را بر اساس Ruleها گزارش می‌کند، Formatting ظاهر کد را یکسان می‌کند، Testing رفتار مورد انتظار را می‌آزماید، Debugging علت خطا را پیدا می‌کند و Build خروجی موردنیاز برای محیط مقصد را تولید می‌کند. استفاده از این مراحل به‌صورت مکمل، کیفیت و قابلیت تکرار فرآیند توسعه را افزایش می‌دهد.

Senior — Golden Answer

یک Workflow حرفه‌ای صرفاً مجموعه‌ای از ابزارها نیست؛ فرآیندی است که مراحل توسعه، بررسی و آماده‌سازی انتشار را به یکدیگر متصل می‌کند. هر مرحله باید مسئله مشخصی را پوشش دهد و نتیجه آن مبنای تصمیم‌گیری بعدی باشد. قابلیت تکرار نصب Dependencyها، بررسی کیفیت کد، آزمودن رفتارهای مهم، تشخیص علت خطا و بررسی خروجی Build باعث می‌شود ریسک انتشار کاهش یابد؛ هرچند هیچ مرحله یا ابزار واحدی صحت کامل نرم‌افزار را تضمین نمی‌کند.

Conclusion

در این فصل دیدیم که توسعه JavaScript فقط نوشتن Source Code نیست. یک پروژه زمانی برای انتشار آماده می‌شود که اجزای آن سازمان‌دهی شده باشند، Dependencyها قابل مدیریت باشند، کد و رفتار برنامه بررسی شده باشند و خروجی نهایی برای محیط مقصد آماده باشد.

با این حال، یک Workflow مناسب به‌تنهایی تمام مسائل مهندسی نرم‌افزار را حل نمی‌کند. وقتی Application رشد می‌کند، مسئله جدیدی شکل می‌گیرد: چگونه مسئولیت‌ها را میان بخش‌های مختلف تقسیم کنیم تا تغییر یک قسمت، نگهداری و توسعه قسمت‌های دیگر را دشوار نکند؟

این پرسش ما را به موضوع فصل بعد می‌رساند: Application Architecture Fundamentals؛ جایی که بررسی می‌کنیم چگونه یک Script ساده را به Applicationی با مسئولیت‌های مشخص و قابل نگهداری تبدیل کنیم.
