Chapter 66 — Error Handling
Chapter Goal

در پایان این فصل، خواننده باید بتواند خطاهای Synchronous و Asynchronous را تشخیص دهد، مسیر انتقال آن‌ها را تحلیل کند و برای مدیریت آن‌ها رفتار قابل اعتمادی در برنامه طراحی کند.

Core Question

چگونه خطاهای Synchronous و Asynchronous را به‌صورت قابل اعتماد مدیریت کنیم؟

مقدمه

برنامه‌ها همیشه دقیقاً مطابق انتظار ما اجرا نمی‌شوند.

ممکن است کاربر ورودی نامعتبری وارد کند، داده‌ای که برنامه انتظار دارد وجود نداشته باشد، یک Function نتواند عملیات موردنظر را انجام دهد یا یک عملیات Asynchronous با شکست مواجه شود. در تمام این شرایط، مسئله فقط این نیست که «خطا رخ داده است»؛ مسئله مهم‌تر این است که برنامه پس از وقوع خطا چه رفتاری باید داشته باشد؟

اگر خطا نادیده گرفته شود، ممکن است اجرای برنامه در نقطه‌ای غیرمنتظره متوقف شود. اگر خطا بدون اطلاعات کافی منتقل شود، پیدا کردن علت آن دشوار می‌شود. و اگر هر خطا در هر نقطه‌ای مدیریت شود، کنترل جریان برنامه پیچیده خواهد شد.

پس یک برنامه قابل اعتماد باید بتواند بین مسیر اجرای عادی و مسیر خطا تفاوت ایجاد کند؛ یعنی بتواند خطا را ایجاد کند، آن را به بخش مسئول منتقل کند و در نقطه مناسب درباره ادامه یا پایان عملیات تصمیم بگیرد.

JavaScript این مدل را با مجموعه‌ای از مکانیزم‌های مرتبط فراهم می‌کند. ابتدا باید بفهمیم Error چیست و چگونه یک وضعیت خطا را بیان می‌کند. سپس باید بتوانیم چنین وضعیتی را با throw وارد جریان خطا کنیم. بعد از آن، try و catch به ما اجازه می‌دهند محل وقوع و محل مدیریت خطا را از یکدیگر جدا کنیم و finally امکان اجرای بخشی از Logic را که باید در پایان انجام شود فراهم می‌کند.

اما این مدل فقط برای اجرای Synchronous نیست. در دنیای Promise، شکست عملیات به شکل Rejection بیان می‌شود و در نتیجه، مدیریت خطا باید با مدل Asynchronous نیز هماهنگ شود. در نهایت، مدیریت خطا فقط گرفتن آن نیست؛ برنامه باید بتواند پس از خطا نیز در صورت امکان به یک وضعیت قابل استفاده بازگردد.

بنابراین Error Handling یک دستور یا Syntax مستقل نیست؛ بلکه مدلی برای کنترل مسیر اجرای برنامه در هنگام وقوع وضعیت‌های غیرمنتظره است.

Error؛ وقتی اجرای عادی دیگر ممکن نیست

در یک برنامه معمولی، Execution بر اساس یک مسیر مشخص جلو می‌رود. یک Function اجرا می‌شود، مقدار موردنیاز را دریافت می‌کند، محاسبه‌ای انجام می‌دهد و نتیجه را برمی‌گرداند.

اما همیشه چنین مسیری ممکن نیست.

فرض کنید برنامه‌ای قرار است اطلاعات یک کاربر را از یک داده دریافت کند:

const user = getUser();

console.log(user.name);

اگر getUser() نتواند داده مورد انتظار را فراهم کند، برنامه دیگر نمی‌تواند با همان فرض قبلی ادامه دهد. اینجا یک Error Condition به وجود آمده است؛ یعنی شرایطی که ادامه اجرای عادی Logic را با مشکل مواجه می‌کند.

نکته مهم این است که Error لزوماً به معنای یک Bug در خود JavaScript نیست. ممکن است برنامه از نظر Syntax کاملاً صحیح باشد، اما در زمان اجرا با شرایطی مواجه شود که باید به آن واکنش نشان دهد.

برای مثال:

داده‌ای که انتظار داشتیم وجود ندارد.
ورودی دریافت‌شده معتبر نیست.
یک عملیات موردنیاز قابل انجام نیست.
یک Function نمی‌تواند نتیجه معتبر تولید کند.

در چنین شرایطی برنامه به یک راه برای اعلام خطا و انتقال کنترل به مسیر مناسب نیاز دارد.

اینجاست که throw وارد مدل Error Handling می‌شود.

از وقوع Error تا اعلام آن با throw

وجود یک وضعیت خطا به‌تنهایی کافی نیست. بخشی از برنامه که متوجه خطا شده است باید بتواند آن را به Runtime اعلام کند.

JavaScript برای این کار از throw استفاده می‌کند.

function getUser(id) {
if (!id) {
throw new Error('User ID is required');
}

return { id, name: 'Omid' };
}

در اینجا Function تشخیص داده است که بدون id نمی‌تواند عملیات موردنظر را انجام دهد. بنابراین به‌جای اینکه با یک وضعیت نامعتبر ادامه دهد، خطا را با throw وارد جریان Error می‌کند.

از اینجا یک نکته مهم شکل می‌گیرد:

throw خودش نوع Error را تعریف نمی‌کند؛ بلکه یک Value را وارد جریان Exception می‌کند.

از نظر زبان JavaScript، می‌توان Valueهای مختلفی را throw کرد:

throw 'Something went wrong';
throw 404;
throw { message: 'Invalid user' };

اما این کار معمولاً انتخاب مناسبی نیست. در کد حرفه‌ای، استفاده از یک Object از نوع Error اطلاعات و رفتار استانداردتری در اختیار برنامه قرار می‌دهد:

throw new Error('User ID is required');

بنابراین رابطه این دو مفهوم را باید دقیق ببینیم:

Error وضعیت خطا را توصیف می‌کند؛ throw آن وضعیت را وارد مسیر انتقال خطا می‌کند.

اما این خطا دقیقاً چه چیزی را با خود منتقل می‌کند؟

Error Object؛ خطا فقط یک پیام نیست

وقتی می‌نویسیم:

throw new Error('User ID is required');

یک Error Object ایجاد کرده‌ایم.

این Object فقط برای نمایش یک متن نیست. اطلاعاتی درباره وضعیت خطا در اختیار برنامه قرار می‌دهد.

مهم‌ترین Property آن message است:

const error = new Error('User ID is required');

console.log(error.message);

خروجی:

User ID is required

Property دیگری که برای تشخیص نوع خطا استفاده می‌شود name است:

console.log(error.name);

برای یک Error معمولی، مقدار آن معمولاً:

Error

است.

در بسیاری از Runtimeها، اطلاعات Stack نیز در Error وجود دارد و مسیر اجرای منتهی به خطا را برای Debugging قابل مشاهده می‌کند.

پس وقتی یک Error ایجاد می‌کنیم، در واقع یک Object حاوی اطلاعات مربوط به خطا داریم، نه صرفاً یک String.

این موضوع در زمان مدیریت خطا اهمیت پیدا می‌کند؛ زیرا بخشی که خطا را دریافت می‌کند باید بتواند اطلاعات آن را بررسی کند.

اما هنوز یک سؤال اساسی باقی مانده است:

اگر throw خطا را وارد جریان اجرا کند، چه بخشی از برنامه باید آن را دریافت و مدیریت کند؟

try و catch؛ جدا کردن مسیر موفقیت از مسیر خطا

اگر یک Error با throw ایجاد شود و هیچ بخش مناسبی آن را مدیریت نکند، اجرای جاری نمی‌تواند مانند قبل ادامه پیدا کند.

JavaScript برای مشخص کردن محل مدیریت خطا از try و catch استفاده می‌کند.

try {
const user = getUser();
console.log(user.name);
} catch (error) {
console.log(error.message);
}

معنای این ساختار ساده است:

try بخشی از Logic را مشخص می‌کند که ممکن است در آن خطا رخ دهد.
catch مشخص می‌کند اگر در آن بخش خطایی رخ داد، چه کاری انجام شود.

در مثال بالا اگر getUser() خطایی با throw ایجاد کند، اجرای عادی بخش try متوقف می‌شود و کنترل به catch منتقل می‌شود.

یعنی catch فقط زمانی اجرا می‌شود که در try یک Exception رخ داده باشد.

این موضوع یک اصل مهم در طراحی Error Handling ایجاد می‌کند:

محل وقوع خطا و محل تصمیم‌گیری درباره خطا الزاماً یکی نیستند.

Function ممکن است فقط مسئول تشخیص مشکل باشد:

function getUser(id) {
if (!id) {
throw new Error('User ID is required');
}

return { id, name: 'Omid' };
}

اما تصمیم درباره اینکه پس از این خطا چه اتفاقی بیفتد می‌تواند در سطح دیگری انجام شود:

try {
const user = getUser();
console.log(user.name);
} catch (error) {
console.log(error.message);
}

این جداسازی باعث می‌شود Function بتواند خطا را اعلام کند و Caller بتواند درباره نحوه مدیریت آن تصمیم بگیرد.

خطا چگونه به catch می‌رسد؟

فرض کنید چند Function پشت سر هم فراخوانی می‌شوند:

function loadUser() {
validateUser();
}

function validateUser() {
throw new Error('Invalid user');
}

try {
loadUser();
} catch (error) {
console.log(error.message);
}

خطا در validateUser() ایجاد شده است، اما catch در سطح دیگری قرار دارد.

اگر در مسیر اجرای Functionها catch مناسبی پیدا شود، Exception به آن نقطه منتقل می‌شود.

بنابراین لازم نیست هر Function الزاماً خطایی را که ایجاد می‌کند همان‌جا مدیریت کند. این موضوع امکان می‌دهد مسئولیت تشخیص خطا از مسئولیت تصمیم‌گیری درباره واکنش به خطا جدا شود.

اما یک سؤال دیگر باقی می‌ماند:

آیا همیشه باید بعد از try و catch بخشی از Logic را اجرا کنیم؟

برای پاسخ به این سؤال باید finally را وارد مدل کنیم.

finally؛ کاری که باید در پایان انجام شود

گاهی یک بخش از Logic باید در پایان عملیات اجرا شود؛ چه عملیات موفق باشد و چه با Error مواجه شود.

برای این وضعیت از finally استفاده می‌کنیم:

try {
const user = getUser();
console.log(user.name);
} catch (error) {
console.log(error.message);
} finally {
console.log('Operation finished');
}

finally برای اجرای Logic نهایی استفاده می‌شود؛ یعنی بخشی که نباید وابسته به موفق یا ناموفق بودن مسیر اصلی باشد.

به‌عنوان مثال:

let isProcessing = true;

try {
processData();
} catch (error) {
console.log(error.message);
} finally {
isProcessing = false;
}

در اینجا مهم نیست processData() موفق شود یا Error ایجاد کند؛ در پایان، وضعیت Processing باید به حالت مناسب بازگردد.

پس تا اینجا مدل Synchronous Error Handling کامل‌تر شده است:

Error
↓
throw
↓
Error Object
↓
try
↓
catch
↓
finally

یعنی:

یک وضعیت خطا ایجاد می‌شود.
خطا با throw وارد جریان Exception می‌شود.
معمولاً یک Error Object اطلاعات آن را نگه می‌دارد.
try محدوده‌ای را مشخص می‌کند که ممکن است خطا در آن رخ دهد.
catch مسیر مدیریت خطا را مشخص می‌کند.
finally Logic نهایی را مستقل از نتیجه مسیر اجرا می‌کند.

اما این مدل تاکنون بر یک فرض مهم استوار بود: خطا در جریان اجرای Synchronous رخ می‌دهد.

وقتی وارد Promise می‌شویم، مدل انتقال نتیجه کمی متفاوت می‌شود.

Promise Rejection؛ وقتی شکست بخشی از نتیجه Async است

Promise نتیجه یک عملیات Asynchronous را در آینده نشان می‌دهد. این نتیجه می‌تواند موفق باشد یا شکست بخورد.

در فصل Promise با دو وضعیت اصلی آشنا شدیم:

Fulfilled
Rejected

وقتی Promise نتواند عملیات موردنظر را با موفقیت به پایان برساند، وارد وضعیت Rejected می‌شود.

مثلاً:

const promise = new Promise((resolve, reject) => {
reject(new Error('Request failed'));
});

در اینجا reject() نشان می‌دهد که Promise با شکست مواجه شده است.

بنابراین در دنیای Promise، شکست عملیات با Promise Rejection بیان می‌شود.

برای دریافت این خطا می‌توان از catch() استفاده کرد:

promise
.then(data => {
console.log(data);
})
.catch(error => {
console.log(error.message);
});

این ساختار از نظر مفهومی شبیه همان مدلی است که قبلاً دیدیم:

Synchronous
throw
↓
catch

Promise
reject
↓
catch

اما نباید این دو را کاملاً یکسان فرض کنیم.

در حالت Synchronous، throw یک Exception را در جریان اجرای فعلی ایجاد می‌کند.

در Promise، reject باعث می‌شود Promise وارد وضعیت Rejected شود و این شکست از طریق Promise Chain منتقل شود.

این تفاوت زمانی اهمیت بیشتری پیدا می‌کند که از async و await استفاده کنیم.

Async Error؛ همان مسئله با مسیر متفاوت

یک async function همیشه یک Promise برمی‌گرداند.

بنابراین اگر درون آن Function خطایی ایجاد شود، نتیجه آن برای Caller به شکل یک Rejected Promise ظاهر می‌شود.

مثال:

async function getUser() {
throw new Error('User not found');
}

فراخوانی:

getUser();

یک Promise دریافت می‌کند که به دلیل خطای ایجادشده، Rejected است.

به همین دلیل می‌توان خطا را با catch() دریافت کرد:

getUser()
.catch(error => {
console.log(error.message);
});

اما async/await اجازه می‌دهد همان جریان را با Syntax دیگری مدیریت کنیم:

async function loadUser() {
try {
const user = await getUser();
console.log(user);
} catch (error) {
console.log(error.message);
}
}

اینجا try/catch دوباره ظاهر شده است، اما این بار در یک Async Flow.

این موضوع بسیار مهم است:

try/catch فقط برای خطاهای Synchronous نیست؛ در یک async function می‌توان از آن برای دریافت Rejection حاصل از await نیز استفاده کرد.

بنابراین اگر Promise مربوط به await به حالت Rejected برود، کنترل از مسیر موفقیت خارج شده و به catch منتقل می‌شود.

می‌توان این رابطه را چنین خلاصه کرد:

Promise Rejection
↓
await
↓
try / catch
↓
Async Error Handling

مثلاً:

async function loadRecipe() {
try {
const response = await fetch('/api/recipe');

    if (!response.ok) {
      throw new Error('Failed to load recipe');
    }

    const recipe = await response.json();

    return recipe;
} catch (error) {
console.log(error.message);
}
}

در این مثال دو مسیر متفاوت وجود دارد:

fetch() می‌تواند با یک مشکل شبکه‌ای مواجه شود و Promise را Reject کند.
برنامه نیز می‌تواند با بررسی Response تشخیص دهد که وضعیت مورد انتظار را دریافت نکرده و خودش یک Error ایجاد کند.

در هر دو حالت، catch محل مدیریت خطا است.

اما اینجا یک نکته بسیار مهم وجود دارد: مدیریت خطا به معنی حذف خطا نیست.

هدف Error Handling این نیست که برنامه هر خطایی را مخفی کند. هدف این است که برنامه بعد از وقوع خطا رفتار مشخص و قابل پیش‌بینی داشته باشد.

Recovery؛ بعد از خطا چه اتفاقی بیفتد؟

تا اینجا یاد گرفتیم چگونه Error را ایجاد و دریافت کنیم. اما یک برنامه واقعی نمی‌تواند در همه موارد به این پاسخ محدود شود:

catch (error) {
console.log(error.message);
}

نمایش پیام خطا فقط بخشی از مسئله است.

سؤال مهم‌تر این است:

بعد از اینکه خطا را فهمیدیم، برنامه باید چه کار کند؟

این همان مفهوم Recovery است.

Recovery یعنی برنامه پس از وقوع خطا، در صورت امکان، به یک وضعیت قابل استفاده بازگردد یا مسیر مناسبی برای ادامه کار انتخاب کند.

نوع Recovery به مسئله بستگی دارد.

گاهی باید یک مقدار جایگزین استفاده شود:

function getSettings() {
try {
return loadSettings();
} catch (error) {
return {};
}
}

گاهی باید خطا به لایه بالاتر منتقل شود، چون این Function مسئول تصمیم‌گیری نهایی نیست:

function loadUser() {
try {
return getUser();
} catch (error) {
throw error;
}
}

و گاهی باید به کاربر اطلاع داده شود که عملیات انجام نشده است.

بنابراین Recovery یک دستور خاص JavaScript نیست. یک تصمیم مهندسی درباره وضعیت برنامه پس از خطا است.

این تصمیم باید با توجه به نوع خطا و مسئولیت آن بخش از Application گرفته شود.

هر Error را نباید مخفی کرد

یکی از اشتباهات رایج این است که برای جلوگیری از متوقف شدن برنامه، تمام خطاها را بگیریم و هیچ کاری با آن‌ها نکنیم:

try {
doSomething();
} catch (error) {
}

این کار Error را از بین نمی‌برد؛ فقط اطلاعات آن را پنهان می‌کند.

اگر برنامه نمی‌تواند Recovery مناسبی انجام دهد، بهتر است خطا به لایه‌ای منتقل شود که مسئول تصمیم‌گیری درباره آن است.

بنابراین Error Handling موفق به معنای «گرفتن همه خطاها» نیست؛ بلکه به معنای قرار دادن خطا در نقطه مناسب برای تصمیم‌گیری است.

throw

خطا کجا ایجاد شده است؟

اگر این مسیر مشخص باشد، throw، Error، try، catch، finally و Promise Rejection دیگر مجموعه‌ای از Syntaxهای جداگانه نیستند؛ بلکه بخش‌های مختلف یک مدل واحد برای کنترل شکست هستند.

Best Practices
1. برای Errorهای واقعی از Error استفاده کنید

به‌جای:

throw 'Request failed';

ترجیح دهید:

throw new Error('Request failed');

این کار اطلاعات استانداردتری در اختیار بخش دریافت‌کننده خطا قرار می‌دهد.

2. Error را در نزدیک‌ترین نقطه مناسب ایجاد کنید

Functionی که می‌تواند تشخیص دهد ورودی یا وضعیت نامعتبر است، باید بتواند خطا را اعلام کند.

اما لازم نیست همان Function مسئول تصمیم‌گیری نهایی درباره Recovery باشد.

3. Error را بی‌دلیل مخفی نکنید

این ساختار:

try {
doSomething();
} catch (error) {
}

اطلاعات مهمی را از دست می‌دهد.

اگر Recovery مشخصی وجود ندارد، باید درباره محل مناسب انتقال خطا تصمیم گرفت.

4. catch را برای تصمیم‌گیری استفاده کنید

هدف catch فقط چاپ کردن Error نیست.

باید مشخص باشد که بعد از دریافت خطا چه رفتاری لازم است:

نمایش پیام مناسب
استفاده از مقدار جایگزین
ثبت اطلاعات لازم
انتقال خطا به لایه بالاتر
یا پایان دادن کنترل‌شده به عملیات
5. finally را برای Logic نهایی استفاده کنید

اگر عملیاتی باید مستقل از موفق یا ناموفق بودن اجرا انجام شود، finally می‌تواند محل مناسبی برای آن باشد.

6. در Async Code، Rejection را فراموش نکنید

داشتن Promise به معنی حذف Error نیست.

Promise می‌تواند Rejected شود و این Rejection باید در جریان مناسب مدیریت شود.

7. Error Handling را با Recovery یکی ندانید

گرفتن Error یک مرحله است.

تصمیم درباره اینکه Application بعد از آن چه کاری انجام دهد، مرحله دیگری است.

Common Mistakes
اشتباه اول: تصور اینکه throw فقط Error Object می‌گیرد

از نظر JavaScript، throw می‌تواند Valueهای مختلفی را پرتاب کند؛ اما در کد حرفه‌ای استفاده از Error معمولاً انتخاب مناسب‌تری است.

اشتباه دوم: قرار دادن تمام Logic داخل try

try نباید به یک ظرف بزرگ برای تمام کد تبدیل شود.

باید محدوده‌ای را پوشش دهد که واقعاً ممکن است در آن Error موردنظر رخ دهد.

اشتباه سوم: خالی گذاشتن catch

گرفتن Error و نادیده گرفتن آن معمولاً فقط تشخیص مشکل را سخت‌تر می‌کند.

اشتباه چهارم: تصور اینکه catch فقط برای Synchronous Code است

Promise Rejection نیز می‌تواند با catch() مدیریت شود و Rejection حاصل از await نیز می‌تواند به catch مربوط به try منتقل شود.

اشتباه پنجم: تصور اینکه Error Handling یعنی جلوگیری از Error

Error Handling به معنای جلوگیری از همه خطاها نیست.

بعضی خطاها اجتناب‌ناپذیرند. هدف این است که Application در برابر آن‌ها رفتار مشخص و قابل کنترل داشته باشد.

اشتباه ششم: مخلوط کردن Error Handling با Debugging

Debugging برای پیدا کردن علت و مسیر مشکل است؛ Error Handling برای تعیین رفتار برنامه هنگام وقوع خطاست.

این دو به یکدیگر مرتبط‌اند، اما یک مفهوم واحد نیستند.

Summary

Error Handling مدلی برای کنترل رفتار برنامه در زمان وقوع وضعیت‌های غیرمنتظره است.

ابتدا یک Error Condition شکل می‌گیرد. اگر برنامه بخواهد این وضعیت را به‌صورت صریح وارد جریان خطا کند، از throw استفاده می‌کند. معمولاً Value پرتاب‌شده یک Error Object است که اطلاعاتی مانند message و name را در اختیار برنامه قرار می‌دهد.

try محدوده‌ای را مشخص می‌کند که ممکن است خطا در آن رخ دهد و catch مسیر مدیریت آن خطا را فراهم می‌کند. finally نیز برای Logicی استفاده می‌شود که باید در پایان عملیات اجرا شود.

در Async JavaScript، شکست عملیات معمولاً به شکل Promise Rejection بیان می‌شود. این Rejection با catch() قابل مدیریت است و هنگام استفاده از async/await می‌توان آن را با try/catch مدیریت کرد.

اما هدف نهایی Error Handling فقط دریافت Error نیست. Application باید در صورت امکان بتواند پس از خطا به یک وضعیت قابل استفاده بازگردد یا خطا را به بخش مسئول تصمیم‌گیری منتقل کند. این همان Recovery است.

Key Takeaways
Error بیان‌کننده یک وضعیت غیرعادی در اجرای برنامه است.
throw یک Value را وارد جریان Exception می‌کند.
استفاده از Error برای بیان خطا، اطلاعات ساختاریافته‌تری فراهم می‌کند.
try محدوده‌ای را مشخص می‌کند که ممکن است در آن خطا رخ دهد.
catch مسیر مدیریت Error را مشخص می‌کند.
finally برای Logic نهایی مستقل از موفقیت یا شکست مناسب است.
Promise شکست عملیات را با وضعیت Rejected بیان می‌کند.
Promise Rejection با catch() قابل مدیریت است.
Error ایجادشده در async function به شکل Rejected Promise برای Caller ظاهر می‌شود.
await می‌تواند Rejection را به catch مربوط به try منتقل کند.
Error Handling با Recovery یکسان نیست.
هدف Error Handling، کنترل رفتار Application هنگام شکست است؛ نه مخفی کردن خطاها.
Technical Interview
Junior
سؤال 1: throw در JavaScript چه کاری انجام می‌دهد؟

throw یک Value را به‌عنوان Exception وارد جریان اجرای برنامه می‌کند. در کد حرفه‌ای معمولاً از Error یا یکی از انواع آن استفاده می‌شود.

سؤال 2: تفاوت try و catch چیست؟

try محدوده‌ای از کد را مشخص می‌کند که ممکن است در آن Error رخ دهد و catch در صورت وقوع Error، مسیر مدیریت آن را فراهم می‌کند.

سؤال 3: finally چه کاربردی دارد؟

finally برای اجرای Logic نهایی استفاده می‌شود؛ یعنی بخشی که مستقل از موفق یا ناموفق بودن مسیر اصلی باید اجرا شود.

Mid-Level
سؤال 4: تفاوت throw new Error() و Promise.reject() چیست؟

throw یک Exception را وارد جریان اجرای جاری می‌کند، در حالی که Promise.reject() یک Promise را در وضعیت Rejected قرار می‌دهد. این دو در Synchronous و Promise-based Error Handling نقش‌های متفاوتی دارند.

سؤال 5: اگر داخل یک async function خطایی throw شود چه اتفاقی می‌افتد؟

async function یک Promise برمی‌گرداند؛ بنابراین Error پرتاب‌شده باعث می‌شود Promise برگشتی به حالت Rejected برود.

سؤال 6: آیا try/catch فقط برای Synchronous Errorهاست؟

خیر. در یک async function می‌توان خطاهای مربوط به Promiseهایی را که با await منتظرشان هستیم نیز با try/catch مدیریت کرد.

سؤال 7: چرا نباید Error را در catch نادیده گرفت؟

زیرا نادیده گرفتن Error اطلاعات مربوط به شکست را پنهان می‌کند و می‌تواند باعث شود Application در وضعیت نامشخصی ادامه دهد یا تشخیص مشکل دشوار شود.

Senior
سؤال 8: چرا محل ایجاد Error نباید الزاماً محل مدیریت آن باشد؟

زیرا ایجاد Error و تصمیم‌گیری درباره واکنش به آن دو Responsibility متفاوت هستند. یک Function ممکن است فقط بتواند وضعیت نامعتبر را تشخیص دهد، در حالی که لایه بالاتر اطلاعات کافی برای تصمیم‌گیری درباره Recovery یا ارائه Feedback دارد.

سؤال 9: Error Handling خوب چه تفاوتی با Error Suppression دارد؟

Error Handling یعنی خطا شناسایی، منتقل و در نقطه مناسب مدیریت شود. Error Suppression یعنی خطا بدون تصمیم‌گیری واقعی پنهان یا نادیده گرفته شود. Suppression ممکن است مشکل اصلی را از دید برنامه‌نویس مخفی کند.

سؤال 10: Recovery در Error Handling به چه معناست؟

Recovery یعنی Application پس از وقوع خطا، در صورت امکان، به یک وضعیت قابل استفاده بازگردد یا یک مسیر جایگزین و مشخص برای ادامه یا پایان عملیات انتخاب کند.

سؤال 11: چرا Promise Rejection باید بخشی از مدل Error Handling محسوب شود؟

زیرا عملیات Asynchronous نیز می‌تواند شکست بخورد. Promise این شکست را با وضعیت Rejected بیان می‌کند؛ بنابراین Application باید همانند Errorهای Synchronous برای این مسیر نیز رفتار مشخصی داشته باشد.

Golden Answers
throw چیست؟

throw یک Value را به‌عنوان Exception وارد جریان اجرای JavaScript می‌کند. در کد حرفه‌ای معمولاً یک Error Object پرتاب می‌شود تا اطلاعات استانداردی درباره خطا در اختیار بخش دریافت‌کننده قرار گیرد.

try/catch چگونه کار می‌کند؟

try محدوده‌ای را مشخص می‌کند که ممکن است در آن Exception رخ دهد و catch مسیر مدیریت آن Exception را فراهم می‌کند. اگر در try خطایی رخ دهد، اجرای عادی آن بخش متوقف شده و کنترل به catch منتقل می‌شود.

Promise Rejection چه ارتباطی با Error Handling دارد؟

Promise می‌تواند به‌جای Fulfilled شدن، Rejected شود. این Rejection بیانگر شکست عملیات Asynchronous است و می‌تواند با catch() یا در صورت استفاده از await با try/catch مدیریت شود.

Error در async function چه می‌شود؟

چون async function همیشه Promise برمی‌گرداند، Error پرتاب‌شده درون آن به Rejection همان Promise تبدیل می‌شود.

Recovery چیست؟

Recovery تصمیمی است که Application پس از دریافت Error درباره ادامه یا پایان عملیات می‌گیرد؛ مانند استفاده از مقدار جایگزین، ارائه Feedback مناسب یا انتقال Error به لایه‌ای که مسئول تصمیم‌گیری است.

Conclusion

یک Application قابل اعتماد فقط برای مسیر موفقیت طراحی نمی‌شود.

در یک مسیر واقعی، ممکن است داده نامعتبر باشد، عملیات قابل انجام نباشد یا یک Promise با شکست مواجه شود. بنابراین بخشی از طراحی Application باید به این سؤال اختصاص پیدا کند که وقتی مسیر عادی دیگر ممکن نیست، کنترل چگونه ادامه پیدا کند؟

در JavaScript، این مدل از Error آغاز می‌شود. throw امکان اعلام و انتقال Exception را فراهم می‌کند و Error Object اطلاعات لازم درباره آن را در اختیار برنامه قرار می‌دهد. try و catch مسیر اجرای عادی و مسیر خطا را از یکدیگر جدا می‌کنند و finally امکان اجرای Logic نهایی را فراهم می‌کند.

در Async JavaScript، همین مسئله در قالب Promise Rejection ظاهر می‌شود و async/await امکان می‌دهد این مسیر را با همان مدل try/catch مدیریت کنیم.

اما نقطه پایان Error Handling، گرفتن خطا نیست. یک Application زمانی رفتار قابل اعتمادتری دارد که بداند پس از خطا چه تصمیمی باید بگیرد؛ یعنی بتواند در صورت امکان Recovery کند و در غیر این صورت، خطا را به مسئول مناسب منتقل کند.

اکنون مدل Error Handling را در اختیار داریم؛ اما هنوز یک مسئله بزرگ‌تر باقی مانده است: در Applicationهای واقعی، معمولاً فقط یک عملیات Asynchronous وجود ندارد. چند عملیات ممکن است به‌صورت ترتیبی یا هم‌زمان اجرا شوند، وضعیت‌های مختلفی ایجاد کنند و در طول اجرای خود نیازمند کنترل باشند.
